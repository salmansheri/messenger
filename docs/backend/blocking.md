# Backend: Blocking

Moved out of CLAUDE.md; read it before working in this area and keep it up to date.

- Blocking (#57; #58-#62, the backend of it, `BlockService`, see `docs/adr/0006-a-block-withholds-messages-silently.md` and GLOSSARY "Blocking"): `PUT /api/v1/users/{userId}/block` blocks and `DELETE` unblocks (both 204 and idempotent: repeating the current state changes nothing, sends no event and costs nothing); `GET /api/v1/users/me/blocks` lists the caller's Blocked Users `{userId, displayName, avatarUrl, blockedAt}` newest first. A Block is a row in `user_block` (migration `V17`, unique per pair, one way, never yourself) and can only be made against someone the caller shares a **Direct conversation** with: yourself, an unknown User and someone you share only a Group with (or nothing) are the uniform 404 'User not found.', so the endpoint cannot probe for accounts. Making or lifting a Block takes that Direct conversation's row lock (`findByIdForUpdate`, the lock sends take), so a send is unambiguously before or after it. Real changes are limited to `app.blocks.max-changes-per-hour` (20) per User through `RateLimiter` (429 with `Retry-After`; counted under the lock, after the no-op check, so a repeat is free, but before the write). Every `ConversationResponse` carries the viewer's own `blocked` flag: true only on a Direct conversation whose other Participant the viewer blocked (one query per list, `UserBlockRepository.findBlockedAmong`); the Blocked User's responses never reflect it. Event `block.changed {userId, blocked}` goes to the blocker's own sessions only, after commit, only on a real change; nothing ever goes to the Blocked User. While the Block lasts the **blocker** cannot send (incl. replies and images; 409 'Unblock this person to send Messages.'), edit or react (409 'Unblock this person to change Messages.') in that Direct conversation (`BlockService.requireMaySend`/`requireMayChange`, called under the conversation lock); hiding for themselves, taking back their own reaction and deleting their own Messages for everyone still work, a retry of a send stored before the Block still answers 200 (ADR 0001), and Groups they share are untouched; a reaction's Message is checked first, so an unknown one is still the uniform 404. The Blocked User is not stopped from sending. **Withheld Messages (#59)**: a Message the Blocked User stores in that Direct conversation while the Block lasts is marked under the conversation lock with `message.withheld_from` = the blocker (migration `V18`; `BlockService.withholderOf`; set once, never cleared, so Unblock releases nothing and a Message stored just before the Block is ordinary). The sender sees nothing different (201, next `seq`, their history and tabs, retries 200). For the blocker it is treated like a Message they hid themselves: every `findVisible…` page (also `aroundSeq`), `lastMessage` (`ConversationAssembler.latestVisible`), both searches and Reply quotes (`QuoteResolver.quoteFor`: unavailable) skip it; acting on it by id (react, hide, edit, delete, reply to) is the uniform 404; `message.created`, `message.updated` and `reaction.changed` (`RealtimeEventsImpl`) and push (`PushServiceImpl`) skip the blocker. **Unread**: `Participant.unreadCount(lastSeq, withheld)` subtracts the Messages withheld from the viewer after their read position (`MessageRepository.countWithheldUnread`, one query per list; also the receipts response and `unread.updated`); hidden Messages still count. **Status**: `MessageStatuses` answers `SENT` for any Withheld Message for ever. **Frontier** (`RealtimeEventsImpl.frontierLimits`): a sender of Withheld Messages is never told a `receipts.updated` position at or past their first Withheld Message in that Conversation, and the blocker never one past the latest Message they can see (sending reads up to the new Message, which would otherwise announce it). Known limits: because the frontier is one number, after Unblock the Blocked User's live ticks in that Direct conversation never move past the first Withheld Message (fetched pages and `lastMessage` carry the right status, `READ` included); the blocker can still get a `receipts.updated` at the moment the Blocked User sends, when that send is what marks the blocker's own Messages read (it carries nothing newer than what the blocker sees); the blocker can infer that Withheld Messages exist from a gap in the Sequence numbers after Unblock, or from `POST /receipts` accepting a position beyond the latest Message they see (ADR 0006: silence is not perfect). **List order (#60)**: Withheld Messages are not activity for the blocker, so a Conversation's `updatedAt` in the blocker's `ConversationResponse` is the time of the latest Message not withheld from them (or the Conversation's start when there is none; `ConversationAssembler.visibleActivity`, one query, `MessageRepository.findVisibleActivity`, answering only for Conversations that hold Messages withheld from the viewer, so every other one keeps `updated_at`), and `GET /conversations` sorts by that (pinned first, then `updatedAt` descending, a stable sort over the database's `updated_at, id` order so ties keep it); the frontend orders by the same `updatedAt`. The Blocked User's own list moves as for any send. This relies on a Direct conversation's `updated_at` moving only on a send; if anything else ever bumps it, `visibleActivity` must take that into account. **The Blocked User's Reactions, edits and typing (#61)**: while the Block lasts the blocker sees none of the Blocked User's Reactions in that Direct conversation, also ones placed before the Block (`ReactionLoader.of(messages, viewerId)` leaves out reactions by someone the viewer blocks in a Direct conversation: history and every page, `lastMessage`, send, edit and reaction responses; one query when nobody blocks anyone, two otherwise; Groups hide nothing), and they show again as they stand after Unblock (nothing is deleted; the blocker's client refetches after `block.changed`, #63). Events are built per audience for reactions too (`ReactionLoader.ofEach`, grouped with the quote in `RealtimeEventsImpl.publishMessage`). The Blocked User's reacting is accepted and answered with their own reactions; `reaction.changed` from them, `message.updated` for their edits and `typing.changed` from them skip the blocker (`UserBlockRepository.findBlockersInDirect`, one query per event); their deletions for everyone still reach the blocker (event and placeholder). Known limit (ADR 0004): no earlier text is kept, so an edit the Blocked User makes within the 15-minute window to a Message sent before the Block shows to the blocker at their next fetch. **Presence and Groups (#62)**: the two never see each other's presence, either way, in any Conversation (the Direct one and shared Groups): `GET /presence` leaves the other out of each one's list and `presence.changed` is not sent between them (`UserBlockRepository.findBlockedEitherWayWith`, everyone the User blocks or is blocked by, one query per list or announcement), so the Blocked User sees the blocker as having no presence at all. The Blocked User creating a Group that includes the blocker (the whole request) or adding the blocker to one gets the same 404 'No user found.' as an unknown or unverified User (`GroupServiceImpl.requireNotBlockedBy`, checked after the "already in this Group" 409 so a Participant another Admin added reads the same to everyone); other Admins can still add the blocker, and Messages, Reactions and typing in shared Groups are untouched. Known limits: Block and Unblock send no presence event, so a client keeps the other's last presence until it next fetches (the blocker's refetches on `block.changed`, #63; the Blocked User's at its next fetch or reconnect); lookup by email still finds the blocker while adding them is refused, so the Block is not undetectable (ADR 0006). Tests: `BlockTests`.
