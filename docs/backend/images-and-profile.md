# Backend: image uploads, image Messages, display name and Avatars

Moved out of CLAUDE.md; read it before working in this area and keep it up to date.

- Image uploads (#40, `AttachmentService`, see `docs/adr/0005-images-are-served-by-short-lived-signed-urls.md`): `POST /api/v1/attachments` (multipart part `file`) stores one image for the caller and returns 201 `{id, width, height, url, thumbnailUrl}`; the URLs are signed (`app.storage.url-ttl`, 15 minutes) and only the uploader gets them here; nothing refers to the upload yet (sending it with a Message is the next ticket, which must make it attachable once and only by its owner: `attachment.message_id` is the link, null until then; migration `V12`, with `ON DELETE SET NULL` so a removed Message detaches its image and the sweep deletes the files). **Storage is local disk**, behind the `ObjectStorage` port in `lib` (`put`, `delete`, `signedUrl`, `open`), so another store (a cloud bucket) is only another implementation. `LocalObjectStorage` writes files under `app.storage.directory` (env `STORAGE_DIRECTORY`, default `data/uploads` relative to where the app runs, git-ignored; written to a `.part` file and moved into place), and `signedUrl` builds `{app.storage.public-base-url}/api/v1/files/{key}?expires=…&signature=…` where the signature is an HMAC-SHA256 of key and expiry with `app.storage.signing-secret` (env `STORAGE_SIGNING_SECRET`; change it in production, links stop working when it changes). `FileController` (`GET /api/v1/files/{*key}`, public in `SecurityConfig`: an `<img>` cannot send a bearer token, the signature is the credential) answers a bad signature, a lapsed link, an unknown file or a key that would leave the directory with one uniform 404; it sets the type from the file name, `private, max-age=60`, `nosniff` and `Cross-Origin-Resource-Policy: cross-origin`. Expiry uses the `Clock` bean, so tests move it. Several instances can share the directory (a network disk) because the secret is configuration; there are no backups, no size accounting and no disk quota. **Validation is by decoding** (`lib/Images`): PNG, JPEG, WebP (TwelveMonkeys reader) and GIF, whatever the file name or declared type says; empty and not-an-image are 400, over 10 MB is 413 (`PayloadTooLargeException`), over 8000 pixels on a side or over 40 million pixels is a 400 (checked from the header before decoding, so a small file cannot make us allocate a huge bitmap). The stored copy is re-encoded from the pixels, so no EXIF, GPS or other metadata survives; a JPEG's EXIF orientation is applied first (dimensions are those of the upright image), JPEGs stay JPEG, PNG/GIF/WebP are stored as PNG (a GIF keeps only its first frame), and a thumbnail 480 px wide (same size if narrower) is stored beside it. Uploads are limited to `app.uploads.max-per-minute` (20) per User through `RateLimiter`, counted before the image is processed and separately from sends. Uploads never sent with a Message are removed after `app.uploads.unattached-lifetime` (24h, by the `Clock` bean) by `AbandonedUploadSweeper` every `app.uploads.cleanup-interval` (10 minutes; tests 250ms), which deletes the files and the row; files are removed if saving the row fails. Multipart limits are `spring.servlet.multipart.max-file-size` 10MB / `max-request-size` 11MB; Tomcat closes the connection while an over-limit body is still arriving, so a browser may see a network failure instead of the 413 problem (the handler in `GlobalExceptionHandler` is not covered by a test, since a client cannot observe it reliably): the frontend should check the size itself. Known limits: a failure between storing the files and writing the row can leave stray files if removing them also fails; the sweep handles 100 uploads per run; tests watch `target/test-uploads` to see a file removed (a lapsed link looks the same as a removed file). Tests: `UploadImageTests`.
- Messages with an image (#41, `AttachmentLoader`): `POST /{id}/messages` takes an optional `attachmentId` (an upload made with `POST /attachments`); `body` is then the caption and may be left out (`@ValidCaption`: absent is fine, blank or over 4000 characters is not, error under `errors.body`), and a request with neither is a 400 under `errors.textOrImage` (`SendMessageRequest.isTextOrImage`). The link is `message.attachment_id` (migration `V13`, which also dropped `attachment.message_id`): unique, so an image belongs to at most one Message, and a check lets a Message have a null `body` only while it has an image or is deleted for everyone. The upload is locked (`AttachmentRepository.findByIdForUpdate`, always after the conversation lock) and someone else's, an unknown one and one already sent are one 404 'Attachment not found.' (counted against the send throttle like a failed reply). A retry of the same Client message ID answers 200 when the image is the same and 409 when the image differs or is added or missing (text and reply are compared as before); once a Message is deleted the image is no longer compared. **Every `MessageResponse` has `attachment`** (`{id, width, height, url, thumbnailUrl}` with freshly signed links, null for none and for a Message deleted for everyone): send, edit and reaction responses, history and catch-up pages, `lastMessage` in the list and the `message.created` / `message.updated` events, read in one query per page or list (`AttachmentLoader`). The signed link is not tied to a viewer (it is the same capability for whoever holds it, ADR 0005), so events stay one per audience; who gets the image is decided by who gets the Message (join point, hidden and current Participants as for any Message). An edit changes the caption only (for an image sent alone it adds one; the text cannot be cleared); replying, reacting, hiding and deleting for everyone work as for text. `Previews.of` words a glimpse of a Message: 'Photo', or 'Photo: ' plus the first 100 characters of the caption, in the push body and a Reply's quote text (a quote never carries the image). Known limits: the sweep of never-sent uploads does not lock the row, so a send that picks an upload at the very moment it passes its 24 hours can find its files gone. Tests: `AttachmentMessageTests`.
- Deleting an image Message (#42, `AttachmentService.release`): deleting for everyone sets `body` and `attachment_id` to null on the Message (saved first), marks the upload `removed_at` (migration `V14`; from then on `send` refuses it with the same 404, so a deleted image cannot be sent again) in the same transaction, and after commit (`AfterCommit`) deletes both files; the sweep then deletes the row (every `cleanup-interval`). **A storage failure never undoes the deletion**: it is only logged, and `AbandonedUploadSweeper` finds every upload with `removed_at` set (any age; `AttachmentRepository.findAbandoned`) and retries the files and row until they are gone. Until then the previously issued links keep working (the files are still there); once removed they answer 404. A repeated delete returns before touching anything (still a 204, even with storage down), and the response and `message.updated` event carry no `attachment`. A link already handed out is a capability for its 15 minutes (ADR 0005), so someone who saved the URL elsewhere only loses it when the files go. Tests: `DeleteImageMessageTests` (with `FaultyObjectStorage`, a test wrapper around the local storage that can make deletes fail, reset before each test).
- Display name (#45, `UserService.updateDisplayName`): `PATCH /api/v1/users/me` `{displayName}` (`@ValidDisplayName`, the sign-up rules: not blank, at most 100 code points, no NUL; surrounding spaces are dropped) returns the profile. The name is stored on the User row and Messages still carry only `senderId`, so every reader sees the current name on old Messages. **Saving the name already held changes nothing, sends no event and does not count against the allowance**; a real change counts: `app.profile.max-name-changes-per-hour` (5) per User through `RateLimiter` (429 with `Retry-After`; counted before the write, and a refused attempt stores nothing). Event `profile.changed {userId, displayName}` (no conversation id, like `presence.changed`) goes after commit to everyone who shares any Conversation with the User (`ParticipantRepository.findCoParticipantIds`) and to the User's own sessions, so a person who left every shared Conversation hears nothing; best effort, and a client that missed it learns the name at its next list fetch (`participants[].displayName` in every Conversation is read from the User row). Lookup by email is unchanged. The change takes the User row lock (`findByIdForUpdate`), so two at once are counted, stored and announced in one order. Tests: `DisplayNameTests`.
- Avatars (#46, `AvatarService`, ADR 0005): `PUT /api/v1/users/me/avatar` (multipart `file`; 200 with the profile) sets and `DELETE /api/v1/users/me/avatar` (204 whether or not there is one) removes. `Images.avatar` shares the checks of attachments (`prepare`: empty and not-an-image are 400, over 10 MB 413, over 8000 px or 40 million pixels 400, decoded not trusted by name; the stored copy is re-encoded so no EXIF or GPS survives; a JPEG's orientation is applied first) and then takes the **centre square** and scales it to **256x256** (always, a small picture is enlarged); JPEG stays JPEG, PNG/GIF/WebP are stored as PNG. The key is `avatars/{userId}/{random}.{ext}` and lives in `users.avatar_key` (migration `V15`): **a new picture is a new key**, so its link differs from the old one and the old file can go. Limited to `app.profile.max-avatar-changes-per-hour` (10) per User through `RateLimiter` (counted before the picture is processed; 429 with `Retry-After`), separate from the upload allowance of attachments because every change is announced to everyone the User shares a Conversation with. **Where the link appears**: `ParticipantSummary.avatarUrl` on every `ConversationResponse` (only the viewer's own Conversations, so only people who share one with the User) and `UserProfile.avatarUrl` on `GET`/`PATCH /users/me` and the `PUT` answer (the owner); `UserSummary` (lookup by email) stays id and name only. The link is `AvatarLinks.urlOf(key)`, signed for `app.storage.url-ttl` (15 minutes) on every response, like attachments, so a client refetches the list when one has run out. **Removed files**: replacing or removing records the old key in `stale_file` in the same transaction (`StaleFileService.discard`), deletes the file after commit, and `AbandonedUploadSweeper` (which now also calls `StaleFileService.sweep`) retries any that failed and then forgets the row, so a failed deletion never blocks the change and never leaks the file; the new file is removed again whenever the transaction does not commit (a synchronisation on completion, so a failure of the commit itself is covered too). Both operations take the User row lock (`findByIdForUpdate`). Event: `profile.changed` again, as `{userId, avatarUrl}` with `avatarUrl` null for a removal (no `displayName` key; a name change has no `avatarUrl` key, so a client applies only the keys present), to the same people as a name change (co-Participants and the owner's sessions); removing when there is none sends nothing. The frontend reads both shapes (#47). Known limits: a crash between storing the new file and the end of the transaction leaves one stray file; a link already handed out stops working when the file is removed, which is right after the change commits; only a failed deletion keeps it alive until the sweep (up to `cleanup-interval`) or its own 15 minutes. Tests: `AvatarTests`, with `FaultyObjectStorage` for the failed-deletion case.
