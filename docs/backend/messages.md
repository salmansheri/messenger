# Backend: Messages, receipts, edit and delete, replies, reactions

Moved out of CLAUDE.md; read it before working in this area and keep it up to date.

- Messages (`/api/v1/conversations/{id}/messages`, see `docs/adr/0001-server-assigned-message-sequence.md`): `POST` `{clientMessageId, body}` (body validated by `@ValidMessageBody`: not blank, at most 4000 characters counted as Unicode code points like the database check, no NUL; stored exactly as sent) returns 201 with the stored Message `{id, conversationId, seq, senderId, clientMessageId, body, createdAt}`, or 200 with the same Message when that sender already used the `clientMessageId` in that conversation with the same text (409 if the text differs). `seq` comes from `conversation.last_seq`, incremented while holding `ConversationRepository.findByIdForUpdate`, so it is gap-free and concurrent sends and retries serialise per conversation; keep that lock for anything that writes Messages. `GET` returns `{messages, hasMore}` in ascending `seq`: newest `limit` (default 50, max 100) by default, `beforeSeq` pages back, `afterSeq` catches up, and `aroundSeq` (#48, where a search result lands) opens a window at a Message: the 25 visible Messages before it, then it and the 25 after (`MessageService.WINDOW_SIDE`; `limit` does not apply; fewer where the Conversation ends), with `hasOlder` and `hasNewer` for each end (`hasMore` is `hasOlder`, the direction it means on the newest page, so code that pages back reads it the same way; both keys are left out of every other page, which only knows its own direction). The Message itself need not be visible (hidden, before the join point, past the latest): the window is the one around its place (a hidden one's slot goes to one more newer Message: 25 before, 26 after), and like every page it skips hidden and pre-join Messages so it stays full. Only one of the three cursors may be given (400 otherwise, after the membership check, so an outsider still sees the 404). Tests: `MessageWindowTests`. A non-participant and an unknown conversation get the same 404. Message `createdAt`/`updated_at` use the microsecond `Clock` bean (Postgres precision) so a value reads back exactly as written. Sending moves the conversation to the top of the list by bumping `updated_at`. Row locks never wait forever: `spring.datasource.hikari.connection-init-sql` sets `lock_timeout` (5s; tests use 1.5s), and a wait that times out becomes a 503 problem with `Retry-After` in `GlobalExceptionHandler`. The history endpoint checks membership before anything else, so a non-participant only ever sees the uniform 404. Membership is checked again under the conversation lock, so a send queued behind a removal is refused. A Participant reads only Messages after `participant.joined_after_seq` (set to the conversation's `last_seq` when they join; history, paging and `lastMessage` all respect it). Sending is throttled per User through `MessageThrottle` (`app.messages.max-sends-per-minute`, default 60, across all Conversations; 429 with `Retry-After`): it is counted before the conversation lock is taken (an over-limit User never queues for it) and only when no stored copy of the Message exists, so a retry the server already answered (200) never counts, and a refused send stores nothing (no gap in `seq`); like the other limits it is spent even if the send then fails for another reason; the counter is a fixed Redis window, so a test cannot move it with the `Clock` and the window's expiry is not tested here. `MessageThrottle.change` is the separate allowance for edits, deletions and reactions (`app.messages.max-changes-per-minute`, 120), unused until those exist; tests reach it through the test-only `ErrorProbeController`. Not done yet: a request-body size cap.
- Receipts (`POST /api/v1/conversations/{id}/receipts` `{deliveredSeq?, readSeq?}`, `ReceiptService`; see GLOSSARY): each Participant has `last_delivered_seq` and `last_read_seq` (migration `V6`, constraint `joined_after_seq <= read <= delivered`; both start at the join point so pre-join history is never unread). Reports move positions forward only, atomically, with `ParticipantRepository.advanceReceipts` (one `greatest(...)` UPDATE, no conversation lock needed because `last_seq` only grows); a lower or late report is ignored with a 200, reading counts as delivering, a position beyond `last_seq` is a 400, and a non-participant gets the uniform 404. Sending advances the sender's own positions to the new Message, so a reply marks everything before it as read (deliberate, like common chat apps; a product decision to revisit if wanted). A Message's `status` (`SENT`/`DELIVERED`/`READ`, `MessageStatuses`) is set only for its sender and is the minimum of the other Participants' positions (a later joiner can't lower it because their positions start at their join point; with nobody else left it stays `SENT`). It appears on the send response, history pages and the list's `lastMessage`. `Participant` is `@DynamicUpdate` so changing a loaded copy (e.g. a role) can never write stale positions back over the atomic `advanceReceipts` update; keep it that way, and use `Participant.unreadCount(lastSeq, withheld)` for the definition. A new Message's status is always `SENT` (nobody can have reported it yet); a retry computes the current status. Positions are reported by clients; nothing marks messages delivered automatically yet (realtime, #11).
- Edit and delete (#28, see `docs/adr/0004-deleted-messages-keep-their-place.md`): `PATCH /{id}/messages/{messageId}` `{body}` edits the caller's own Message (`@ValidMessageBody`; `app.messages.edit-window`, 15 minutes after `createdAt`; sets `editedAt`, keeps no earlier text; the same text changes nothing and sends no event), `DELETE /{id}/messages/{messageId}` deletes it for everyone (204; `app.messages.delete-window`, 1 hour; repeating it is a 204 that changes nothing, even after the window) and `POST /{id}/messages/{messageId}/hide` hides any readable Message from the caller's own view only (204, no window, repeatable). A Message deleted for everyone keeps its row, `seq`, sender and time with `body` null and `deletedAt` set (a check constraint ties the two), so it is a placeholder in history, paging, catch-up and `lastMessage`. Message responses gained `editedAt` and `deletedAt`. Rules: only the sender may edit or delete for everyone (403 for anyone else who can read the Message; Admins get no extra right); a non-participant, an unknown Message, one from another Conversation and one from before the caller joined are all the same 404; a closed window or editing a deleted Message is a 409 with its own wording; edit and delete take the conversation lock and read membership again under it, so a removal queued first wins. Edits and deletions change no `seq`, receipts, status, unread count, `updated_at` order or push (`PushService` skips a Message deleted before the worker ran). `MessageThrottle.change` is counted for edit, delete and hide (before the lock), sharing the 120-a-minute allowance. Hiding is a row in `message_hidden`; history, `beforeSeq` paging and `afterSeq` catch-up filter hidden Messages in the query (`findVisible…`), so pages stay full, and `lastMessage` falls back to the latest Message the viewer has not hidden (null if they hid all). **Decision: `unreadCount` stays plain Sequence arithmetic** (the one exception is Withheld Messages, #59), so a Message hidden before it was read still counts until the read position passes it (a hidden last Message can keep the count above zero until the next Message; the frontend ticket decides how to handle that). Hiding sends no event, so a person's other tabs find out at their next fetch. Event `message.updated` (`message` with `body` or `deletedAt`, and `editedAt`; no `status`) goes to the CURRENT Participants after commit, only when something changed. A retry of the send of an edited or deleted Message (same Client message ID) answers 200 with the stored Message whatever text it carries, because the original text is gone. `message.updated` skips people who joined after the Message and people who hid it. **Known limits**: `afterSeq` catch-up only returns Messages with a higher `seq`, so a client that missed `message.updated` (a dropped socket) never learns of an edit or deletion that way: the frontend must refetch its loaded history pages after a reconnect (a cursor such as `updatedAfter` was left out on purpose); a push already queued or being retried keeps the preview text it was queued with even if the Message is deleted afterwards (the guard only covers a job that has not fanned out yet); `lastMessage` costs one extra query per Conversation whose latest Message the viewer hid; an edit that changes nothing and a repeated delete still use the change allowance. Tests: `EditDeleteMessageTests` (move the clock past the windows and take a fresh token with `loginForTokens`, since tokens last 15 minutes) and `MessageUpdatedEventTests`.
- Replies (#32, `QuoteResolver`): `POST /{id}/messages` takes an optional `replyToMessageId`. It must be a Message of the same Conversation that the replier may read (sent after they joined, and not hidden by them for themselves); anything else, including another Conversation's Message, an unknown id and a non-participant, is the uniform 404 'Message not found.', and replying to a Message already deleted for everyone is a 409 'You cannot reply to a deleted Message.'. Migration `V10` adds `message.reply_to_id` with a composite foreign key `(conversation_id, reply_to_id)` so the database itself refuses a quote across Conversations (`ON DELETE SET NULL (reply_to_id)`, so a Conversation that is removed with its replies cascades cleanly); nothing of the quoted text is copied, so an edit shows through. A reply is otherwise an ordinary Message (Sequence number, receipts, unread, push all as for any send), and a retry with the same Client message ID answers 200 with the stored Message, but the same ID with a different Message to answer (or different text) is the 409. `MessageResponse.replyTo` is a `ReplyQuote {messageId, senderId, text, deleted, unavailable}` **as the viewer sees it**: `text` is the first 100 characters of the quoted Message as it is now (the same `Previews.firstCharacters` the push preview uses, with an ellipsis if cut), `deleted` means it was deleted for everyone (no text), and `unavailable` means it is from before the viewer joined or the viewer hid it for themselves (no text and no sender: a quote must never show someone what they may not read or chose not to see); it goes one level only (the quote of a reply has no quote), a deleted reply has no quote, and editing a reply keeps it. It is on the send response, history and catch-up pages (`afterSeq`), `lastMessage` in the list and the `message.created` / `message.updated` events; quotes are resolved for a whole page or list in one query (`QuoteResolver.resolve`). **Events are built per audience**: a quote differs by reader, so `RealtimeEventsImpl.publishMessage` groups recipients by their quote and sends one event per distinct quote (a non-reply is still one event). A quote read from a live event or a fetch is a snapshot: when the quoted Message is edited or deleted later, no event updates the replies already on a client's screen (the client should take the text from its loaded history if it has it, or refetch). **Pitfall**: `MessageServiceImpl.send` must not load the sender's `Participant` entity before `advanceReceipts` (it reads only `ParticipantRepository.findJoinedAfterSeq`, a scalar): a managed copy loaded earlier is reused by the receipt events computed afterwards, so they would read stale positions and send no `receipts.updated` (`RealtimeTests` caught this). The migration's `ON DELETE SET NULL (reply_to_id)` needs PostgreSQL 15 or later (the compose file uses `postgres:latest`). Known limits: a send that ends in 404 or 409 on its reply target still counts against the send throttle (like every other limit, failed attempts count); the quote on a reply already on screen is not refreshed by an edit or deletion of the quoted Message (the client takes it from its loaded history, or refetches); events for a reply in a large Group cost one distinct-quote grouping pass. Tests: `ReplyTests`.
- Reactions (#33, `ReactionService`): `PUT /{id}/messages/{messageId}/reaction` `{emoji}` puts the caller's reaction on a Message (replacing any other they had there) and `DELETE` takes it away; both are **idempotent** and return the Message as the caller sees it (200), so a retry cannot flip the state: clients decide that choosing the same emoji again means calling `DELETE`. The emoji must be one of six, `Reactions.ALLOWED` in this order: thumbs up, heart (with its variation selector; one typed without it is accepted and stored with it), laughing, surprised, sad, folded hands; anything else is a 400 (the table has a check constraint too). One reaction per Participant per Message (unique `(message_id, user_id)`, migration `V11`). Rules as for edit and reply: a non-participant, an unknown Message, another Conversation's Message, one from before the reactor joined and one they hid for themselves are the uniform 404; a Message deleted for everyone is a 409 'You cannot react to a deleted Message.' and shows no reactions. Reactions are changed under the conversation lock (membership read again under it, so a removal queued first wins) and count against the 120-a-minute change allowance, but touch no Sequence number, receipt, unread count, `updated_at` order or push. **Every `MessageResponse` has `reactions`**, a list of `{emoji, userIds}` grouped by emoji in the offered order (people in the order they reacted; `[]` for none); it is on the send, edit and reaction responses, history and catch-up pages, `lastMessage` in the list and the `message.updated` event (so an edit does not wipe them from a client's screen), read in one query per page or list (`ReactionLoader`). A Participant's reactions in a Conversation are **deleted when they leave or are removed** (`GroupServiceImpl`), so nobody who is gone is counted and coming back starts fresh; the people who remain get one `reactions.cleared {conversationId, userId}` event (only if that person had reacted to something; not one `reaction.changed` per reaction), and a client removes that user from every reaction it has loaded for the Conversation. Event `reaction.changed` (`messageId`, `seq`, `userId`, `emoji` or null for none, `at`) goes after commit to the current Participants who can read the Message and have not hidden it, only when something actually changed; events are best effort and can arrive out of order, so a client orders per `(messageId, userId)` by `at`. Tests: `ReactionTests`.
