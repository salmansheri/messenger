# Backend: Conversations, Groups and their settings

Moved out of CLAUDE.md; read it before working in this area and keep it up to date.

- Conversations (`/api/v1/conversations`): `POST direct` with `{"userId"}` starts a Direct conversation with a verified User and returns 201, or 200 with the same body if the pair already has one (whoever starts it); yourself is a 400, an unknown or unverified User a 404. `GET` lists the caller's Conversations, most recently active (`updated_at`, as the caller can see it: #60) first, with their participants' ids, display names and roles. Schema (`V3`): `conversation` (type DIRECT/GROUP, `direct_key` = both User ids sorted and joined by `:`, unique and required exactly for DIRECT, `last_seq` for message ordering, `updated_at` for list order) and `participant` (unique per conversation and user). Creating a Direct conversation takes a transaction-scoped Postgres advisory lock on the key (`ConversationRepository.lockDirectKey`), so concurrent creators serialise; the unique constraint is only the backstop. Responses are built with three queries per list, not per conversation. `lastMessage` is the latest Message the viewer may read (null until one is sent) and `unreadCount` is `last_seq - the viewer's last_read_seq`, less the Messages withheld from the viewer after it (#59).
- Groups (`/api/v1/conversations`, `GroupService`): `POST groups` `{name, userIds}` (name 1-100 characters; 1-255 other verified Users, duplicates and yourself ignored, any unknown or unverified one is a 404 for the whole request) makes the caller ADMIN and the rest MEMBER; `PATCH /{id}` `{name}` renames; `POST /{id}/participants` `{userId}` adds (409 if already in or the group has 256); `DELETE /{id}/participants/{userId}` removes (not yourself: 400, use leave); `POST /{id}/participants/{userId}/promote` makes an ADMIN (idempotent); `POST /{id}/leave`; `GET /{id}` returns one conversation. Admin-only changes give a Participant who is not an admin a 403, a non-participant the uniform 404, and a Direct conversation a 400. Every change takes `ConversationRepository.findByIdForUpdate` and reads the caller's membership again under it. When the last admin leaves, the earliest-joined remaining Participant (ties by user id) becomes admin; when the last Participant leaves the conversation row is deleted and the database cascades to participants and messages. Adding someone back after removal starts a fresh join point. Creating groups is throttled per User (`app.groups.max-created-per-hour`, default 20, failed attempts count, 429 with `Retry-After`). `participants` are listed admins first, then by join time. Responses are built by the package-private `ConversationAssembler` for a given viewer; the join-point rule lives on `Participant` (`canRead`, `readableAfter`). A removed sender's old messages stay, but their name is no longer in `participants` (messages carry only `senderId`).
- Mute, archive and pin (#29, `ConversationSettingsService`): `PATCH /api/v1/conversations/{id}/settings` `{mute?: NONE|EIGHT_HOURS|ONE_WEEK|ALWAYS, archived?, pinned?}` changes only what is present and returns the Conversation as the caller sees it (an empty body, or archived and pinned both true, is a 400; a non-participant gets the uniform 404). The settings are columns on `participant` (`muted_until`, `muted_forever`, `archived`, `pinned`; migration `V9`, with a check that a Conversation is never archived and pinned), so they are private to their owner and **leaving or being removed clears them** (re-adding starts with the defaults). Every `ConversationResponse` carries the viewer's own `settings {muted, mutedUntil, archived, pinned}`: `muted` without `mutedUntil` is muted for ever, a mute that has run out simply reads as not muted (there is no job and no event at expiry; clients compute from `mutedUntil`). Mute only silences push: `PushServiceImpl.queueDeliveries` skips recipients muted at the moment the worker runs (the `Clock` bean), while unread counts and live events are untouched. Archiving never undoes itself when a Message arrives; archiving a pinned Conversation unpins it (one request); pinning an archived one is a 409 "Unarchive it before pinning." (unarchive and pin in one request is fine); a fourth pin is a 409 "You can pin at most 3 Conversations."; all settings changes of one User are serialised with an advisory lock taken before the participant row is read (`ParticipantRepository.lockPinsOf`), so concurrent pins respect the limit and concurrent archive and pin never act on a stale row; the check constraint is only the backstop. `GET /conversations` lists pinned Conversations first and the rest by recent activity (the pinned ones keep that order among themselves); the Archived view is the frontend's filter on `settings.archived`, the server does not split the list. `settings.changed` (`settings`) goes to the owner's sessions only, and only when something actually changed. Known limits: a push job or delivery already queued (or waiting in the 30-second retry) is not re-checked against a mute that began or lapsed since the fan-out ran; archived Conversations are still returned in the list, in their normal place, for the frontend to filter. Tests: `ConversationSettingsTests`.
