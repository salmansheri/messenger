# Frontend: Conversation list, Groups, settings, your name

Moved out of CLAUDE.md; read it before working in this area and keep it up to date.

- Conversations (#19): `/app` (the index), `/app/c/[id]` and `/app/new` sit in the route group `app/app/(conversations)`, whose layout is `ConversationsFrame`: the index (`ConversationIndex`, one `GET /conversations` for the whole list via `useConversations`, query `listOptions()`, key `listQueryKey()`) beside the other side on a desktop (`md:`), and on a phone one or the other, told apart by the address (`/app` is the index; anything below is the other side, with a "← Conversations" link back in `PaneHeader`). Settings is outside the group, full width. What a row shows comes from `features/conversations/present.ts` (`conversationTitle`: the other person's name or the Group's name; `lastLine`: one line, "You: " for your own, the sender's name in a Group; `formatWhen`: time today, "Yesterday", weekday, then date, in the viewer's time zone; `unreadLabel`). `useConversationList()` gives the list together with your id (`pending` / `error` / `ready`). Every screen has exactly one top-level heading: the list's own (`h1`, which also labels its `nav`) when nothing is open, the open screen's (`PaneHeader`, `h1`) otherwise, with the list's heading then an `h2`; a test counts them on every screen. Unread counts are spoken as "1 unread Message" / "2 unread Messages" (the badge shows only the number). The open Conversation is found in the already loaded list, so opening it asks the server for nothing, and an id that is not in the list (unknown or someone else's) gets one plain "not found". Starting a Direct conversation is `POST /users/lookup` by exact email, then `POST /conversations/direct` (201 new, 200 existing: the same URL either way), then the list is refetched before navigating; your own address is noticed before the second call (the server also answers 400; `startDirectOutcome` decides the message and whether it belongs under the address or on the form), an unknown or unverified address is the same message (the backend's lookup is deliberately identical for both), and 429 uses the general "You are doing that too often" wording (`messageFor`); `codesMessageFor` is the code-specific one for screens that send codes. The whole signed-in area sits under one `Suspense` in `app/app/layout.tsx`, because `usePathname`/`useParams` on a dynamic route are only known per request (dev mode does not complain, `bun run build` does, so run the build). Messages are in the next note, realtime in the one after.
- Groups (#24, `features/groups`): **Creating** is a screen, not an overlay: `/app/new/group` (linked from `/app/new`), `CreateGroupForm`: a name (`checkGroupName`, the backend's rules: not blank, 100 code points, no NUL) and people added by exact email; each address is looked up when added (`POST /users/lookup`) and shown as a named chip (`addPerson` in `members.ts`, pure: yourself, a repeat and the 255-person cap are refused with a reason). The address box is the shared `AddAddressField` (used here and in the panel; not a `<form>`, so Enter adds and never creates or submits anything around it): it checks the address, ignores Add while an add is under way, empties the box only if it still holds the address just added (the person may already be typing the next one) and keeps focus in it (also after a chip is removed). The chip list is kept in a ref as well as in state so an add that finishes later reads the list as it is by then. Create needs a name and at least one person; success refetches the list and opens the Group. **Managing** is `GroupPanel`, the `<details>` "Participants (n)" in a Group's header (it replaces the plain list of #23; `ParticipantList` takes a per-person `actions` render prop): an Admin gets `RenameForm` (a TanStack Form with `groupNameSchema`, keyed by the current name so another Admin's rename replaces what is typed; renaming to the same name sends nothing), Make Admin (accessible name \"Make Admin (Ada Lovelace)\", so it contains the visible text) and Remove per other Participant, which wait for each other (one change at a time), and "Add a person by email" (lookup, then add); every member gets Leave Group, which asks first and says "You are its only Admin, so another member will become Admin" when it applies (the backend decides who: the earliest-joined remaining Participant). What a person may do follows their role in `conversation.participants`; if the server refuses anyway, `groupFailure` (pure, `wording.ts`) puts the reason in place: 403 \"Only an Admin can change this Group.\", 409 already in this Group / the Group is full (256; the only case told apart by the backend's own words), 404 by what was asked (adding or creating: the address, with the same words as starting a Direct conversation; removing or promoting: \"That person is no longer in this Group.\"; otherwise the Group), field errors under the name. A failure clears when the next action starts, when the name or address is edited, or when leaving is cancelled. Nothing is applied to the screen by hand after an action: `useGroupActions` asks for the list (and that Conversation's presence) again, and the backend's `conversation.changed` makes everyone else do the same, so a rename, join, promotion, removal or departure shows live for every Participant; a removed or departed person sees the Conversation leave their list and, if open, \"You are no longer part of this Conversation.\"; leaving navigates to `/app`. The generated mutations (`createMutation`, `renameMutation`, `addParticipantMutation`, `removeParticipantMutation`, `promoteMutation`, `leaveMutation`) are used as they are; adding by email is a custom `mutationFn` (lookup then add). e2e: `e2e/support/navigation.ts` has `index`, `rowFor` and `showIndex` (exact \"Conversations\" link, because a removed Participant's screen also has \"Back to your Conversations\"); a 403 is simulated with `page.route` (the UI never offers a non-Admin a control, so the real server never has to refuse one); a first visit to a page compiles it in development and can take longer than a click assertion allows, so a test that needs a new page `goto`s it. Known limits: only the 256 cap wording is unit-tested (creating a 256-person Group in a browser is not worth it), there is no way to rename or change a Group from a phone-sized header other than opening the panel, and a person who has just been removed sees their panel replaced rather than animated away.
- Mute, archive and pin (#34, `features/conversations`): every `ConversationResponse` has the viewer's own `settings {muted, mutedUntil, archived, pinned}` (the generated `ConversationSettings`; `mutedUntil` may be JSON null). The pure rules are in `settings.ts` (Vitest): `isMuted(settings, now)` checks the end itself, because a timed mute can run out after the list was fetched with no event to say so; `orderConversations` puts pinned first and then by `updatedAt` descending (a Conversation with no time counts as oldest, so the comparator is consistent), keeping the given order for ties, and is used by `applyToList` both for `message.created` (a new Message moves its row to the top of its block, never above the pinned ones) and for the new `settings.changed` event; `withSettings` replaces one Conversation's settings and re-orders (the same list when nothing differs, nothing when unknown, which makes the reducer ask for the list again); `archivedHasUnread` drives the dot. `parseEvent` reads `settings.changed` (to the person's own sessions only, so a second tab sees a change live). The person's own change goes through `useUpdateSettings` (`updateSettingsMutation`), whose answer is put into the list by `recordSettings` (`sync.ts`) through the same `patchList` as events, with the same 'restart a fetch that is under way' rule. **The open Conversation's header** has a three-dot `ConversationMenu` (`DropdownMenu` and `MenuItem` in `components/ui/dropdown-menu.tsx`, shared with the Message menu; `nextMenuIndex` is in `components/ui/menu-keys.ts`): Mute for 8 hours / for a week / always, Unmute (only while muted), Archive/Unarchive, Pin/Unpin. Nothing is shown before the server says yes; a refusal keeps the menu open and says why in the server's own words (`settingsFailureMessage`: 409 'You can pin at most 3 Conversations.' or 'Unarchive it before pinning.', never the general 409 account wording). A line under the name says what is set (`settingsLine`: 'Pinned · Muted until 20:00 · Archived'; 'Muted until tomorrow 08:30' and 'Muted until Tue 17 Mar, 08:30' for later times). **The index** marks a pinned row with a pin and a muted one with a struck bell (both with sr-only words 'Pinned.' / 'Muted.' inside the row link, so they are part of its name), a muted row's unread badge is outlined instead of filled (it still counts), and archived Conversations are a view of their own (`Archived (n)` button, with a dot and 'has unread Messages' when one has unread; 'Back to your Conversations'): archiving makes the row leave the main list without changing the view the person is looking at, opening a different Conversation shows the view it is in, and an Archived view with nothing in it falls back to the main list. e2e: `conversation-settings.spec.ts` (pin with a second tab live, the cap, archive and the Archived view with its dot, pinning an archived one, muting and unmuting, a busy server, keyboard; axe on the list, the Archived view, the open menu and a refused pin); `updateSettingsVia` sets state through the backend. Known limits: a response to the person's own change and an event for another can arrive out of order (settings carry no version), which a reconnect or the next refetch corrects; a timed mute that ends while nothing re-renders keeps its marker until the next update; unarchiving the open Conversation while other archived ones remain leaves the person in the Archived view without it; push is silenced by the server, nothing here changes how the browser itself notifies.
- Changing your name (#45, `features/session`): Settings has a 'Your name' section with `ProfileForm` (TanStack Form with the sign-up `displayNameSchema`, check on submit then on change like every form; `useServerProblems` shows the server's reason under the field; `nameChangeFailureMessage` (pure, `wording.ts`) words a 429 with how long to wait, 'You have changed your name too often. Try again in 30 minutes.'). Saving the name already held asks the server for nothing. On success the answer goes through `recordProfile` (`features/realtime/sync.ts`) and 'Name saved.' (a `role=status`) shows; a name changed in another session replaces what is in the box (the form is keyed by the held name, like the Group rename form; the saved notice lives in the parent so the remount that a successful save causes does not lose it). **Live**: `profile.changed {userId, displayName}` is parsed by `parseEvent`; `applyToList` (via the pure `withProfile`, which also carries Avatars since #47) renames that person in every loaded Conversation's `participants`, which is where list rows, headers, the names above runs of Messages and the Group panel all read names, and returns the same list when nobody has that name already or the person is in none of them; `recordProfile` also updates the cached profile (`useMe`) when it is the signed-in person's own, so their other tabs follow. It goes through `patchList`, so a list request under way is asked for again instead of patched. Verification is Vitest (event parsing, the list patch, `handleEvent`, wording), typecheck and lint. **Not exercised in a browser**: the form (focus on a failed submit, the saved notice being announced), the live rename on a second screen, and axe on the section; they were read from the code.
