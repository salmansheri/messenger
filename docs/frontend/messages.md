# Frontend: the Message view and everything done to Messages

Moved out of CLAUDE.md; read it before working in this area and keep it up to date.

- Message view (#20): `MessageView` (`features/messages`) sits under the open Conversation's header (`key={id}`, so state resets per Conversation). History is a TanStack `useInfiniteQuery` (`messagesKey(id)` (the generated `historyInfiniteQueryKey({ path: { conversationId } })`), newest page first, `beforeSeq` for older ones; the first page is 50 or enough to reach the first unread Message, at most 100); `confirmedMessages` merges pages by `seq`, `buildTimeline` (pure, tested) adds the day headings (`formatDay`), the "Unread" mark and the name on the first Message of each run by one sender. The first unread `seq` and unread count are taken **once when the view opens** (`firstUnreadSeq(conversation)`), not live. Scrolling: it positions itself once (first unread mark, else the bottom; if the first unread is older than what was loaded, the top), loads older Messages when within 120px of the top (or via the "Earlier Messages" button) and then adds the height it gained to `scrollTop` so the Message being read does not move, stays pinned to the bottom while near it, and shows "Jump to latest" when more than 240px away. `h-dvh` on the signed-in shell and `min-h-0` down the frame are what give the Message list its own scroll area; other pages scroll inside `main`. Sending is `createOutbox` (`outbox.ts`, framework-free, Vitest): `submit` shows the Message as "Sending…" at once with a client Message ID chosen once, sends go out one at a time in written order (a failed one does not hold back later ones), success first calls `onSent`, which puts the stored Message into the history cache (`addMessageToHistory`, which realtime will reuse) and invalidates the Conversation list, and only then removes the entry (never a moment with neither on screen), failure shows "Not sent." with the reason and a Retry that reuses the same ID (a repeat the server already stored answers 200, which counts as success); a pending entry whose `clientMessageId` is already in the history is hidden. The outbox lives in the view, so a Message still failed when the person navigates away is forgotten. `checkMessageBody` mirrors the backend (not blank, 4000 code points, no NUL) and trims the ends but keeps inner line breaks; Enter sends, Shift+Enter makes a new line. Bodies render `whitespace-pre-wrap` with `overflow-wrap:anywhere`; links are not made clickable. e2e: `page.route` with `route.fetch()` then `route.abort()` simulates a lost answer (the server stored it); `messagesVia`/`readUpToVia` in `e2e/support/backend.ts` read the server's copy and set a read position so a test can have a known first unread Message. History uses `gcTime: 0`, so reopening a Conversation always loads fresh (positioning on stale cached pages left the view at an old bottom); only a failed *first* load replaces the view, a failed older page leaves everything and shows a notice above the list; the top of the list is a fixed-height row ("Earlier Messages" or "Start of this Conversation") so reaching the oldest Message does not move the page. Known limits: with about 90+ unread the first unread Message is not sought beyond the first page (the view opens at the top of what loaded), there is no send timeout (one hung request holds later sends), a retried older Message takes a later `seq`, pending Messages show the client's clock until confirmed, and the text is trimmed at both ends (the backend would store it as sent). Not done: marking Messages delivered or read (#22), live arrival (#21), a Group sender who left shows as "Someone who left".
- Send throttle (#30): a send the backend refuses with 429 (`MessageThrottle`, 60 new Messages a minute per User) is an ordinary failed send: 'Not sent.' plus the reason and a Retry that reuses the Client message ID. The reason comes from `sendFailureMessage` (`features/messages/wording.ts`, pure, Vitest): a 429 reads 'You are sending Messages too often. Try again in N seconds.' (rounded up, minutes from 60 seconds on via `describeWait`, 'a few seconds' without a `Retry-After`) because the general wording would say 'in a moment' for any wait under a minute; every other failure keeps `messageFor`. Retry is never disabled during the wait (an early press just gets a new 429 and a new count). Known limits: the outbox keeps sending later Messages while one is throttled, so each refused one needs its own Retry; the seconds are a snapshot and do not count down. e2e: the real limit (60) is too costly to spend in a browser, so `states.spec.ts` answers the first POST with an injected 429 + `Retry-After` (the recorded failure-injection exception) and checks the wording, axe on the failed row, one stored copy and that both attempts carry the same Client message ID.
- Edit and delete (#31, `features/messages`): the generated client has `edit`, `deleteForEveryone` and `hide` (and `updateSettings` for #34); a deleted Message arrives as `body: null` (not absent) with `deletedAt`, an unedited one has `editedAt: null`, so test with truthiness, never `!== undefined`. `MessageRow` (`message-row.tsx`) is one Message: its time, an `edited` mark, the text or the placeholder 'This Message was deleted.' (italic, no actions but 'Delete for me'), and a three-dot button at the right of the row (`MessageMenu`; a single tab stop per Message, named 'Options for your/Ada's Message at 14:02') that opens a dropdown `role=menu` of `menuitem`s: own Messages offer Edit and Delete for everyone, every Message offers Delete for me. The menu focuses its first item when it opens, the arrow keys (wrapping), Home and End move through it (`nextMenuIndex`, `menu-keys.ts`), Escape closes it and gives focus back to the button, a click elsewhere closes it, and it opens upward when there is no room below inside the scrolling history; a hidden Message moves focus to a neighbouring row's button before its row goes; the UI does not enforce the 15-minute and 1-hour windows, it shows the server's 409 wording as given (`changeFailureMessage`: a 409 is NOT the general account wording, 403 'Only the sender can do that.', 404 'That Message is no longer there.', 429 names the seconds). Delete for everyone asks inside the menu first (focus on Cancel, back to the 'Delete for everyone' item on cancel; the first-item focus runs only when the menu opens, or it would steal that focus back). The editor replaces the text in place (`aria-label` 'Edit text' on purpose: a name containing 'Message' would collide with the composer's `getByRole('textbox', { name: 'Message' })`): Enter saves, Shift+Enter a new line, Escape cancels, an unchanged text asks the server for nothing, `checkMessageBody` applies, and focus returns to the row's three-dot button. Nothing is shown before the server says yes; then `use-message-actions.ts` patches the loaded history at once (`updateMessageInHistory`, `markDeletedInHistory`, `removeFromHistory`) and asks for the list again; the `message.updated` event for the same change finds it done. **Events** (`message.updated`, parsed by `parseEvent`): `applyToHistory` replaces the Message in place when it is loaded (ignoring one older than loaded, adding one newer than the newest like a new Message and catching up over a gap), `applyToList` swaps the latest line when it is that Message (asks for the list again if the Message is newer than the line), both through `mergeVersion`/`isNewerVersion` (`versions.ts`): a deletion beats everything, a Message already deleted is never revived by a late edit, a later `editedAt` beats an earlier one, and the sender's own `status` (which events never carry) is kept. The 'restart a fetch that is under way' rule from #21 applies to it too. **Reconnect**: `afterSeq` cannot carry an edit or a deletion (they keep their `seq`), so `catchUp` now runs `refreshHistory` for every loaded history: it fetches the whole loaded range again (`afterSeq` from just before the oldest loaded Message) and `syncRange` makes the cache match, dropping Messages the server no longer shows (hidden in another tab) but never one newer than the newest it returned (it may have arrived live meanwhile); nothing changes unless the whole range was fetched. `lastLine` reads 'This Message was deleted' for a deleted latest Message. **Announcements**: the 'New Messages' `role=log` also reads a Message that was edited or deleted ('Grace edited a Message: Meet at ten', 'Grace deleted a Message', 'You edited a Message' for your own without reading your text back, a count when more than three), tracked by version per `seq` (`versionOf`, `changedMessages`, `changeAnnouncements`). Known limits: the three-dot button is always visible (a hover-only reveal makes axe see invisible text); hiding a Message sends no event, so a person's other tabs only find out at their next fetch or reconnect; a hidden last Message can keep the unread count above zero (the backend counts by Sequence number); there is no window countdown, a refused edit or delete is only learnt by trying. e2e: `edit-delete.spec.ts` (`optionsOf(row)` is the three-dot button, `item(page, name)` a menu item; edit in place with Escape/unchanged/saved, a refused edit, delete for everyone with its question and axe on each state, delete for me, a refused or throttled deletion with injected 409/429/503, edits and deletions made while the socket is down shown after it returns, the announcement log, keyboard-only editing and menu navigation; axe is taken after the pointer leaves a primary button, because mid-way through its hover fade the contrast reads as 4.05); `sendMessageVia` returns the id and `editMessageVia`/`deleteMessageVia` act through the backend.
- Replies (#35, `features/messages`): a **Reply** item is the first entry of a Message's three-dot menu (any confirmed Message that is not deleted, the person's own too). Choosing it puts a draft (`replyDraft`, shaped like the server's `ReplyQuote`) in the Message view's state, focuses the box and shows a strip above it (`role=status`, so 'Replying to Ada Lovelace' and the start of the text are announced) with **Cancel reply**; Escape in the box cancels it too (not while an input method is composing text). The reply is dropped on its own if the Message it answers is deleted meanwhile (`replyTarget`, pure: the server would refuse it with a 409). Sending hands the draft to the outbox (`outbox.submit(body, replyTo)`): the pending entry keeps it, shows the quote while it sends, and **every retry sends the same `replyToMessageId`** along with the same Client message ID. A refused send reads in the server's words (`sendFailureMessage(problem, wasReply)`: 409 passes on `detail`, e.g. 'You cannot reply to a deleted Message.', never the general account wording for a 409; a 404 says 'The Message you were replying to is no longer there.' only for a reply, and 'This Conversation is no longer yours.' for a plain send). A reply whose Message is deleted while it is failed shows 'Message deleted' in its quote (the presenter reads the live Message) but Retry still sends the same target and is refused again: the Message has to be retyped. **The quote in a reply's row** (`QuoteBlock`, `quote.ts`) shows who said it and the start of what they said (two lines), 'Message deleted' for one that was, 'Message not available' for one the person may not see (before they joined, or hidden: the server sends no text and no sender for it); a deleted reply shows none. `quoteView` (pure, Vitest) takes the text from the quoted Message **itself when it is loaded**, so an edit or a deletion shows through at once with no event about the reply (the server's `replyTo` is only a snapshot taken when the reply was fetched, used when the quoted Message is not loaded). When the quoted Message is loaded the quote is a button that goes to it (`jumpTo`: scrolls it to the middle, focuses its row and stops the view snapping back to the bottom; every confirmed row has `data-message-id` and `tabIndex=-1`); when it is not, it is plain words (older history is not fetched to find it). `firstCharacters` counts characters as people do, like the backend's `Previews`. Known limits: the jump only works within the loaded history; the lastMessage line of the list does not show the quote; the person is not told when the Message they were replying to was deleted and the strip simply goes away. Verification is by Vitest, typecheck and lint only (the owner stopped using Playwright), so focus after choosing Reply or cancelling, the scroll of a jump and the axe state of the strip and a quoted row were read from the code, not run.
- Reactions (#36, `features/messages`): the generated client has `react` (PUT) and `unreact` (DELETE) and `MessageResponse.reactions` (`ReactionView {emoji, userIds}`). **CORS**: the backend's `CorsConfig` now allows `PUT` (the API has an endpoint that uses it); the backend tests never make a cross-origin request, so a missing method only shows in a browser as a failed preflight and the request never reaching the server. `reactions.ts` (pure, Vitest) has `REACTIONS` (the six with the names a screen reader says, in the backend's order), `chipName`, `myReaction`, `applyReaction` (one reaction per person: they leave their old group, empty groups go, groups stay in the offered order, people in the order they chose, the same list when nothing changes), `clearUser` and `acceptReaction`. **Events**: `reaction.changed {messageId, userId, emoji|null, at}` and `reactions.cleared {userId}` are applied by `applyToHistory` through `updateReactions` / `clearReactionsOf` (`history.ts`: only a loaded Message that is not deleted, the same history when nothing changes, no reactions and an empty list count as the same); they never touch the list. Because events are best effort and can arrive late, `sync.ts` keeps the time of the last word about each `(messageId, userId)` under the hand-keyed `reactionTimesKey(conversationId)` and refuses an older or repeated one (`acceptReaction`, compared as moments: the server's fractions of a second differ in length), and the 'restart a fetch that is under way' rule applies. A Message's own `message.updated` carries its reactions, so an edit does not wipe them. **After a reconnect** `syncRange` takes the server's reactions for every Message in the refreshed range (they change without a new version of the Message), except a deleted one, which has none. **UI** (`reaction-controls.tsx`): `ReactMenu` is a smile button beside the three dots (`DropdownMenu`, which now opens upward when there is no room below inside the scrolling history) offering the six as `menuitem`s ('Thumbs up', and '(yours: press to remove)' on the person's own); `ReactionChips` shows what people chose under the text as buttons named for what pressing them does, 'React with thumbs up (2)', `aria-pressed` when it is the person's own, with the full names as the accessible description. Pressing your own reaction (chip or picker) removes it: the server's `PUT` only sets and `DELETE` only removes, so the toggle is decided here from the cached reactions. In a Group the chip also shows who ('Ada, Linus +1') and its accessible name ends with those words ('React with thumbs up (3): Ada, Linus +1'), because axe's label-in-name rule wants what is seen to be part of what is said; in a Direct conversation it shows the count only when it is more than one. Nothing is shown before the server says yes; its answer (`setReactionsInHistory`) goes into the loaded history. A refusal shows in the server's own wording under the chips or in the picker, which stays open (`changeFailureMessage`, 429 'You are changing Messages too often…'). A deleted Message has no picker and no chips. e2e: `reactions.spec.ts` (picker of six with axe, one reaction per person, live for a second browser, a Group's who, a dropped socket, a reaction taken away / a Message deleted / a person removed disappearing live, a throttled then busy server, keyboard); `reactVia`/`unreactVia` act through the backend. Known limits: a response to the person's own change carries no time, so a late older event for the same Message and person can briefly show the earlier emoji until the later event arrives; the chips and the picker each own their mutation, so two quick presses in both can race (the server serialises and the events correct the screen); reactions are not announced to screen readers when others make them; a timestamp the client cannot parse is accepted rather than ordered.
- Sending an image (#43, `features/messages`): the generated client regenerated for `upload` (multipart `file`), `MessageResponse.attachment` (`AttachmentResponse {id, width, height, url, thumbnailUrl}`) and `SendMessageRequest.attachmentId`/optional `body`. **Composer** (`composer.tsx`): an icon button named 'Attach image' (`aria-label` and `title`, an inline picture icon in the muted ink colour, 44px square; it opens a hidden `<input type=file accept>`), paste into the box (only when the clipboard holds files; pasting text is untouched) and dropping files on the form (highlighted while dragging); the first file is used (several images are several Messages). `image-file.ts` (pure, Vitest): `checkImageFile`/`chooseImage` refuse before any upload a type that is not PNG/JPEG/WebP/GIF, an empty file and one over 10 MB, in words the person sees under the box (the server decides by decoding, this only saves a pointless upload). A chosen image shows in a `role=status` strip above the box ('Image to send', its file name, 'Remove image') like the reply strip; the text then becomes an optional caption (placeholder 'Add a caption (optional)'; a caption that breaks the text rules still blocks the send). Its size is measured from the picture itself for the row. Preview addresses (`URL.createObjectURL`) are revoked when the image is removed or the composer goes, and by the outbox once the Message is stored. **Outbox** (`outbox.ts`): `submit(body, replyTo, image)`; a pending entry carries `image {file, previewUrl, width, height, attachmentId}`; `run` uploads first (`upload` option, then `sdk.upload`), stores the answer's id on the entry so **a retry after a failed send does not upload again**, and a failed upload is retried with the same Client message ID (nothing was sent yet); `failedAt` says which step failed (`'upload'` is worded by `uploadFailureMessage`: the server's own reason for a refused file, 413 'larger than 10 MB', 429 'sending images too often'; `'send'` by `sendFailureMessage`); a 404 on a send that carried an image forgets the upload id, because the server drops unsent uploads after a day and it may be gone, so the next retry uploads again ('This image could not be sent. Try again.'). An empty body is sent as no text at all. **Row**: `timeline.ts` gives each message item an `image {src, width, height}` (the server's thumbnail; for a Message still being sent the local preview; none when deleted) and `body ''` for an image sent alone; `message-image.tsx` shows it above the caption with its room reserved from the size (`aspect-ratio`, at most 20rem wide, never upscaled past its own width), `loading=lazy`, `alt` 'Image from Ada Lovelace at 14:02' (the row's sender and time). **Wording** shared by the places that show a glimpse: `glimpse.ts` ('Photo', 'Photo: caption', the server's words for pushes and quotes) is used by `quoteView`/`replyDraft` (replying to an image quotes 'Photo…'), `lastLine` in the Conversation list ('Photo', 'You: Photo') and the 'New Messages' log (`announcementOf`: 'Ada sent an image: caption'). **History cache**: `markDeleted` removes the attachment; an edit (response or `message.updated`) replaces the Message with the server's, carrying its fresh links, and an older version arriving late is ignored as before (`versions.test.ts`); the caption editor is the existing one (the text cannot be cleared). Not done here (#44): the full-size overlay, one history refetch when a link has expired followed by a 'Couldn't load image. Retry' placeholder (links last 15 minutes, so an image on a long-open screen can fail to load until then), and refined accessible names. Known limits: an image still being sent when the person leaves the Conversation, or when the page reloads, is forgotten like any unsent Message, even if its upload had succeeded (its preview address leaks until the page reloads); pasting something that carries both an image and text pastes the text; nothing is shown while the upload runs beyond 'Sending…' (no progress bar, out of scope); the file picker's `accept` is a hint only, the check runs on the chosen file. **Not exercised in a browser** (the owner stopped using Playwright): the picker, paste, drag and drop, the strip and its focus after choosing or removing, the thumbnail layout and scroll steadiness as images load, and axe on the new states; they were read from the code. Verification is Vitest (pure modules), typecheck and lint.
- Viewing an image and expired links (#44, `features/messages`): the thumbnail is a button named `imageLabel` ('Image from Ada Lovelace at 14:02', then ': caption' when there is one; `wording.ts`, pure, tested; its `<img>` is `alt=""` because the button carries the name) that opens `ImageViewer` (`image-viewer.tsx`): the browser's own modal `<dialog>` (`showModal`), so it traps focus, closes on Escape and gives focus back to the opener, dressed as dark blurred glass over the whole screen (a full-screen layer inside the dialog with `bg-scrim/70 backdrop-blur-2xl`, not the dialog's `::backdrop`, whose blur is not reliable across browsers, so `::backdrop` itself is transparent) with the picture centred (rounded, soft shadow, at most 78% of the height), its caption (the Message's text) beneath it, a round icon Close button (`aria-label` 'Close', focused first) in the corner and a short fade of the glass and settle of the picture (`.viewer-fade`, `.viewer-in`, which the reduced-motion rule makes instant); a click anywhere outside the picture closes it too (nothing closes the dialog in an effect cleanup: React's development double-run would fire a `close` event and make it vanish), Retry in either place moves focus on to the picture's button or the Close button and the placeholder is a `role=status`, and the full-size link (`TimelineImage.fullSrc`; for a Message still being sent the local preview). The dialog is named like the thumbnail. **Expired links**: signed links last 15 minutes (ADR 0005), so a screen left open can hold dead ones. `image-recovery.ts` is the pure state machine (`nextImageState`, Vitest): the first failed load goes to `refreshing` and asks for fresh links once, silently; a new address that arrives is tried (`showing`, with the single refresh used up) and if that fails too, or none arrives, or asking brought the same link, the picture becomes `failed` (a placeholder 'Couldn't load image.' with Retry, in the same reserved room); a picture that loads again may recover from a later expiry; Retry tries once more with fresh links. `use-image-recovery.ts` is the thin React side (a fetch per move into `refreshing`; the new address is noticed through the `src` prop changing, with a 400 ms wait after the fetch ends before giving up, because the cache update reaches the screen a moment later; the `<img>` is keyed by an attempt counter so Retry reloads even an unchanged address). The fresh links come from `refreshHistory` (the whole loaded range again, as after a reconnect), shared by every image that fails together through one in-flight promise in `MessageView` (`refreshLinks`); `syncRange` takes the server's `attachment` for a Message in the range (not deleted) only when the held links have lapsed (`linksLapsed`: the `expires` in the link, with a minute's margin; unreadable counts as lapsed), so a reconnect does not reload every picture, and always when recovery asks for it (`replaceLinks`, because a link that failed to load cannot be trusted whatever its expiry says, e.g. a clock that is off). A fresh link that turns up after the picture had already given up still shows it (`refreshed` with a changed address is accepted from `failed`). A preview held on this device has no refresh (a failure there is final). Wording for list line, replies and announcements is #43's. Known limits: the dialog does not stop the page behind it from scrolling by wheel on every browser, and there is no zoom or download (out of scope); a very long loaded history makes the refresh several requests; an image failing for another reason (offline, deleted file) shows the placeholder after one refresh round. **Not exercised in a browser**: the dialog (focus on open and on close, Escape, backdrop click, its backdrop colour from the `ink` token), the thumbnail button, the placeholder, and a real expiry (the timing of the fresh link reaching the screen after a refresh); the state machine is covered by Vitest, the rest was read from the code.
- Opening at a Message (#50, `features/messages/window.ts`): `/app/c/[id]?at=SEQ` (read by `ConversationPane` through `targetFrom`, pure: a positive safe whole number, anything else is the latest) opens the Message view on a **window** around that Message (the backend's `aroundSeq`, #48) instead of the newest Messages. A history is **attached** (it holds the newest Message) or **detached** (newer Messages exist on the server that are not loaded); `isDetached` decides it from the newest page and the request that fetched it (`newerParam`: a window page's `hasNewer`, a forward page's `hasMore`; the newest page and older pages never page forward), so nothing extra is stored. `useMessageHistory(conversationId, firstPage, target)` takes its first request from `firstParam` and pages older with `olderParam` (`beforeSeq`; a window reads `hasOlder`, a forward page always has history before it) and newer with `newerParam` (`afterSeq`, TanStack's `fetchPreviousPage`, so the newest page stays `pages[0]` and a refetch of the whole query, which follows `getNextPageParam` from the first stored request, stays contiguous). **While detached**: `applyToHistory` and `withMessage` take no new Message and no edit of a Message that is not loaded (it would sit after a gap; edits, deletions and reactions of loaded Messages still apply), so the person's own sends, catch-up and events never patch the middle, and a new Message does not restart a page of the window being fetched (`sync.ts`; in a busy Group the restarts would starve paging); `catchUpHistory` does nothing and `refreshHistory` (after a reconnect, and the image-link refresh) fetches only up to the window's own newest Message (`refreshBounds`), and drops its answer if the history was started again meanwhile (its first request is no longer in `pageParams`); unsent Messages are not drawn (they belong after the latest); the 'New Messages' log notes newer Messages without reading them out (they come by paging, not live: `useAnnouncements`' `quiet`, latched for the render in which the view attaches); and **reading is not reported** (`useReportReading`'s `enabled`, from the pure `readingReportable`): the read position means everything before it was read, so a window opened further back reports nothing while detached, and once attached only if it also reaches back to the first unread Message (taken when the view opened); delivered reporting (from the list) is unchanged, and reporting resumes with what is then on screen. A detached view shows 'Later Messages' at the bottom (also loaded on scrolling near it, or at once when the window fits on the screen) and 'Jump to latest' always; scrolling never follows the bottom; only one page is asked for at a time (`isFetching`), because a page in one direction cancels one under way in the other. Paging forward until a page reaches the newest Message attaches the history in place; the view then runs `catchUpHistory` once (any Message stored just after that page was read), and from then on live Messages join it as usual. **Jump to latest** while detached (or with a target in the address), and **sending** while detached, call `onLeaveTarget`, which replaces the address without `?at`; the view keeps its state (the outbox survives). An effect on `target` then fetches the new first page itself (`firstParam`: the newest Messages, or another window) after cancelling any request of the query, and puts it in place with `setQueryData` in one step, so the old Messages and the box being typed in stay on screen until the new ones are there (a `resetQueries` would show 'Loading Messages…' and unmount the composer, losing focus; `keepPreviousData` cannot help because a reset query has no previous data); only if that fetch fails is the query reset (its own loading and error states). Going back to the latest lands at the bottom and focuses the composer (not at the Unread mark of when the view opened); a history that already holds the newest Messages only scrolls down. On opening, the view centres the row with that `seq` (`data-message-seq` on every confirmed row), or the next one when it is not shown (hidden, before the person joined), focuses it, and marks it (`data-highlighted`, the `band` colour, fading out after 2.5s through `transition-colors`, which the reduced-motion rule makes instant). Verification is Vitest (`window.test.ts`, `apply-event.test.ts`, `sync.test.ts`), typecheck and lint. **Not exercised in a browser** (the owner stopped using Playwright): the positioning, focus and mark on opening, scrolling and paging both ways, the 'Later Messages' and 'Jump to latest' controls, sending from a window, the reset on a new target, the quiet announcements and the paused read reports; they were read from the code. Nothing links to `?at=` yet: the search screens (#51, #52) will. Known limits: a target that is before the person joined opens at the earliest Message they may read; a history that attached by paging forward is refetched (window focus, reconnect, the 'restart' rule) from its first stored request, an `afterSeq` page, so if more than 50 Messages arrived meanwhile it comes back detached (contiguous, with 'Later Messages'; never a hole); unsent Messages that failed earlier are not drawn while detached (they come back with their Retry at the latest); the first unread mark is the one taken when the view opened.
