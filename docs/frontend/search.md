# Frontend: search

Moved out of CLAUDE.md; read it before working in this area and keep it up to date.

- Search in the open Conversation (#51, `features/search`): a magnifying-glass button in the open Conversation's header (`aria-label` 'Search this Conversation', `aria-expanded`) opens `SearchPanel` under the header (inline, not a dialog; the pane keeps whether it is open and what is typed, both reset for another Conversation, so closing and opening again shows the same results). The box is a labelled `type=search`; what is typed goes through `checkSearchQuery` (pure: trimmed, NUL left out, fewer than 2 code points does nothing (`idle`, no request, no message), more than 100 says 'Search for at most 100 characters.' under the box and sends nothing), and a search starts once typing has paused 300 ms (`useSettled` in `lib/use-settled.ts`; while the next query is being typed the last one's results stay); searches are limited to 30 a minute, so the query never refetches by itself (`staleTime: Infinity`, no refetch on focus or reconnect): only typing, 'More results' and Try again ask. `useConversationSearch` is the generated `searchConversationInfiniteOptions` (`before` is a default paging keyword) with `nextBefore` (pure: the last result's `messageId` while `hasMore`); `resultsOf` (pure) joins the pages newest first, each Message once. A result is a link to `/app/c/{id}?at={seq}` (#50 opens the Conversation there and closes the search) showing who ('You', or 'Someone who left'), when (`resultTime`, pure: the time for today, otherwise the day with the time, 'Yesterday, 21:30') and the snippet: `parseSnippet` (pure) splits the server's U+E000/U+E001 marks into text parts rendered as React text with a `<mark>` (`bg-band`) per match, never as HTML, tolerating marks that do not pair up and never showing a marker character; the snippet is clamped to two lines. 'More results' asks for the next page. The `role=status` line says 'Searching…' and then `resultCountText` ('No Messages found', '1 Message found', '20 Messages found so far, and more'), so a screen reader hears the count. A failure is a notice worded by `searchFailureMessage` (pure: 429 'You are searching too often. Try again in …' through `whenToRetry`/`describeWait`, 404 'This Conversation is no longer yours to search.', otherwise `messageFor`) with Try again (`busy` while it runs; the next page when that is what failed (`isFetchNextPageError`), otherwise the whole search again). Keyboard: the box takes focus on opening, Down moves from the box into the results, Up/Down/Home/End move between them (`nextMenuIndex`, wrapping from the last to the first), Up from the first goes back to the box (the arrows do nothing from the panel's buttons), Escape anywhere in the panel closes it (not while an input method is composing) and gives focus back to the button (`SearchToggle`); a too-long query's message is a `role=alert`. Choosing a result closes the panel and puts focus on the search button until the Message view focuses the row it opens at; choosing the Message the address already opens at changes nothing in the address, so the pane scrolls to and focuses that row itself. Verification is Vitest (`snippet.test.ts`, `query.test.ts`, `results.test.ts`), typecheck and lint. **Not exercised in a browser** (the owner stopped using Playwright): the button and panel, focus on opening and closing, the arrow keys, the pause before searching, the result list and its marks, 'More results', the busy and throttled states with Try again, the count being announced, choosing a result, and axe on any of it; they were read from the code. Known limits: results are not refreshed while the panel is open (a Message edited or deleted meanwhile still shows its old snippet until the search runs again; choosing a deleted one opens its place); the list scrolls inside a fixed height; the search across all Conversations is #52.
- Search across all Conversations (#52, `features/search`): the Conversation list's header has a second `SearchToggle` ('Search all Conversations', next to New) that opens the same `SearchPanel` above the list with `scope: { kind: "all", conversations }` (the panel's scope picks the hook's generated options in `useMessageSearch`: `searchAllInfiniteOptions` or `searchConversationInfiniteOptions`, which share the response shape, hence one cast). Results are grouped by `groupResults` (pure, tested): still newest first, each run from the same Conversation under its name (`conversationTitle`: the other person, or the Group's name; 'Conversation' for one not in the loaded list, rather than dropping its results), each run a nested list labelled by that name (`aria-labelledby`); the sender's name comes from that Conversation's Participants. The panel only opens once the list has loaded (results are named from it). Choosing a result opens `/app/c/{conversationId}?at={seq}` and closes the panel (focus waits on the search button until the Message view focuses the row); choosing the Message the address already opens at changes no address, so the list scrolls to and focuses that row itself (`focusMessageRow`, shared with the pane's search). Known limit: a result in a Conversation the loaded list does not have yet (just joined) opens 'not found' until the list is fetched again. `searchFailureMessage(problem, scope)` keeps the 404 wording for one Conversation only. Verification is Vitest (`groups.test.ts`, `results.test.ts`), typecheck and lint. **Not exercised in a browser**: the list's search button and panel, the grouped results and their labels, choosing a result on a phone (where the list gives way to the Conversation) and on a desktop, and axe on any of it; they were read from the code.
