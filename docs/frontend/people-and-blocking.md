# Frontend: Avatars and Blocking

Moved out of CLAUDE.md; read it before working in this area and keep it up to date.

- Avatars (#47, `features/people`): `Avatar` (`person-avatar.tsx`) is a disc with the person's picture, or their initials (`initialsOf`: first letter of the first and last word, whole graphemes via `Intl.Segmenter`, capitals, '?' for no name) on a tone picked from their id (`toneOf`, FNV-1a over the id into `AVATAR_TONES`; both pure in `avatar.ts`, Vitest). The tones are design tokens `--tone-clay|ochre|moss|sea|slate|plum` in `globals.css`, light tints in the light theme and deep ones in the dark, each carrying `ink` initials at 7.9:1 or more; use the `bg-tone-*` classes, never a hard-coded colour. It is always next to a name, so it is decorative (`aria-hidden`, `alt=""`). A picture that fails to load (a signed link lasts 15 minutes) goes through `useImageRecovery` (the #44 state machine): one silent refetch of the list and the profile (`useProfileRefresh`, `invalidateQueries` with `cancelRefetch: false`, so many pictures failing together share the request in flight), then initials until a different link arrives. Links are signed afresh on every response, so the component keeps the link it already shows while a fresh one points at the same file (`heldLink`, pure, tested: same path via `sameFile` in `lib/signed-link.ts`, which also holds `linkLapsed`, now shared with attachments' `linksLapsed`) and the held one has not failed to load; its expiry does not matter there, because a picture that has loaded stays on screen after its link runs out, and a new picture is a new key, so it is always taken. Without that, every list refetch would download every picture again. Where it is shown: list rows and the open Conversation's header (`conversationAvatar` in `present.ts`: the other person in a Direct conversation, the Group's own name and id for a Group, which has no picture; `PaneHeader` takes an `avatar`), before the name at the start of each run of Messages (`MessageRow` gets an `avatars` map beside `names`; someone who left shows '?') and per person in the Group panel (`ParticipantList`). **Live**: `profile.changed` now parses into `{userId, changes: {displayName?, avatarUrl?}}` (`ProfileChanges`, only the keys the server sent; `avatarUrl: null` is a removal, an event with neither key or a key of the wrong type is dropped); `applyProfileChanges` (pure) puts only those keys into a Participant or profile (the same object when nothing differs); `withProfile` uses it on every loaded Conversation's `participants` and `recordProfile(queryClient, userId, changes)` also on the person's own cached profile. **Settings** has 'Your Avatar' (`AvatarChooser`): the current disc, 'Choose a picture' (a hidden file input; the same `chooseImage` checks as images in Messages: PNG/JPEG/WebP/GIF, not empty, at most 10 MB), then a square preview of the chosen file cut as the server will (`object-cover`, the middle square) with Save Avatar and Cancel, and 'Remove Avatar' while one is set; focus moves to Save after choosing and back to Choose after saving, cancelling or removing; a refusal is worded by `avatarFailureMessage` (`features/session/wording.ts`, pure: 429 with the wait, 413 the 10 MB limit, a 400 in the server's own words) and success says 'Avatar saved.' / 'Avatar removed.' in a `role=status`; the large disc there is the subject rather than decoration beside a name, so a visually hidden line says whether the person has an Avatar. The answer goes through `recordProfile` like the event. A Group has no picture, so its row and header show the initials of its name on a tone from the Conversation id (Group pictures are out of scope in #38). Known limits: an Avatar that mounts afresh (a screen opened again) takes the newest link, so it loads the picture again under that address; the preview shows the browser's own rotation of a JPEG, which matches what the server keeps for ordinary EXIF orientations; nothing shows how far an upload has got. **Not exercised in a browser** (the owner stopped using Playwright): the chooser (picker, preview, focus moves, notices), the discs and their layout in rows, headers, runs and the panel, the refetch after a link runs out, the live change on a second screen and axe on the new states; they were read from the code. Verification is Vitest (`avatar.test.ts`, `events.test.ts`, `apply-event.test.ts`, `sync.test.ts`, `present.test.ts`, `session/wording.test.ts`), typecheck and lint.
- Blocking in the app (#63, `features/conversations`): the generated client gained `block` (PUT), `unblock` (DELETE), `blocks` and `ConversationResponse.blocked` (regenerate with the real app, `./mvnw spring-boot:run`: `spring-boot:test-run` also serves the test-only `ErrorProbeController`, whose endpoints must not reach the committed client). The open Direct conversation's ⋯ `ConversationMenu` offers **Block <name>** and, while blocked, **Unblock <name>**; Block asks first in place of the menu's choices (`DropdownMenu` gained a `replacement` slot, shown instead of the `role=menu` while set, with Escape still closing and the arrow keys left alone): 'Block Grace?' with `BLOCK_EXPLANATION` (they will not be told; their Messages will not reach you, even after you unblock them; you will not see each other's presence), Block and Cancel (focus on Cancel, back to the Block item on cancel). While `blocked`, `MessageView` shows `BlockedNotice` ('You blocked Grace. Unblock to send a Message.', `blockedNotice`, with an Unblock button; focus goes to the composer once it is back) in place of the composer, the header shows no presence line, and each Message offers only what the server still allows (`messageActions`, pure, in `features/messages/actions.ts`: no Reply, React picker or Edit; Delete for everyone on one's own Messages and Delete for me stay); reaction chips stay pressable (taking back one's own reaction is allowed; any other press shows the server's 409). `useBlock` (`blockMutation`/`unblockMutation`) and the event both go through `recordBlock` (`sync.ts`): `withBlocked` (pure, `apply-event.ts`) marks the Direct conversation with that person (same list when nothing changes; the list is asked for again when there is none), and that Conversation's history (the other's reactions hide or come back on the server), its presence and the `blocks` query are asked for again. `parseEvent` reads `block.changed {userId, blocked}`. Refusals are worded by `blockFailureMessage` (pure: 429 'You have blocked or unblocked too often. Try again in …', 409 the server's words, 404 'You no longer share this Conversation with that person.'). When a Block arrives the view stops publishing typing at once (the composer is gone; the server does not drop the blocker's typing towards the Blocked User) and an edit that was open closes (`editingNow` in `MessageRow`; it reopens after Unblock). `directWith` (`present.ts`) finds the Direct conversation with a person for both `withBlocked` and `recordBlock`. Known limits: reaction chips stay pressable while blocked (pressing one's own takes it back, which is allowed; any other is the server's 409); a reply draft chosen before the Block comes back after Unblock; a send already failed or still under way when the Block lands is refused with the server's 409 wording, and its Retry is too. Verification is Vitest (`events.test.ts`, `apply-event.test.ts`, `sync.test.ts`, `actions.test.ts`, `conversations/wording.test.ts`), typecheck, lint and build. **Not exercised in a browser** (the owner stopped using Playwright): the menu items and the in-menu question with its focus moves, the notice and the focus after Unblock, the Message menu and picker while blocked, the header without presence, a Block made in another tab showing live, and axe on any of it; they were read from the code. **Blocked Users in Settings (#64)**: `BlockedUsersSection` (`features/session`, between 'Your Avatar' and 'Session') is the generated `blocksOptions()` query, newest first as the server sends it, each person with their Avatar, name and an Unblock button (named 'Unblock Grace Hopper', containing its visible word); 'You have not blocked anyone.' when empty, a loading status and a failure notice with Try again. Unblocking goes through `useBlock`, so `recordBlock` marks the Direct conversation and takes the person out of the cached list at once (`withoutBlockedUser`, pure, `blocked-users.ts`; then the list is asked for again), which is also what an Unblock from the Conversation's menu, another tab or another device does; a Block made anywhere asks for the list again (it needs the name and picture). Focus after an Unblock goes to the next person still listed, else the nearest one before, else the empty-state line (`focusAfterRemoval(previous, current, removedId)`, pure, so people who left meanwhile, by a second Unblock or another tab, are skipped). Each row being unblocked is remembered in a set and focus is moved once it has left the data, because the row can unmount before its own success callback would run (TanStack drops per-call callbacks of an unmounted component), and only when focus was lost with the row's button (it is on the page body), so it never pulls focus from wherever the person has gone since. `catchUp` also asks for the Blocked Users list after a reconnect. Refusals are `blockFailureMessage(problem, "settings")` under the row (a 404 there reads 'That person can no longer be unblocked here.'); the line under the heading is `BLOCKED_SUMMARY`, kept beside `BLOCK_EXPLANATION`. `useProfileRefresh` now also asks for the Blocked Users list, so their pictures recover after a link runs out. Verification is Vitest (`blocked-users.test.ts`, `sync.test.ts`), typecheck, lint and build; **not exercised in a browser**: the section, its focus moves, a Block in another tab appearing live, and axe on it.
