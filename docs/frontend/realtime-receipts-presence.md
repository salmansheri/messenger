# Frontend: realtime, receipts, unread, presence and typing

Moved out of CLAUDE.md; read it before working in this area and keep it up to date.

- Realtime (#21): `RealtimeProvider` (`features/realtime`, in `app/app/layout.tsx` inside `RequireSession`, so it exists exactly while signed in) owns one `createConnection` (`lib/realtime/connection.ts`, framework-free, `@stomp/stompjs` over the plain WebSocket at `ws://…/ws`, no SockJS). The token is read in `beforeConnect` for every attempt (the current one, or a refresh first if it ran out), reconnects back off 1s to 15s, and only `/user/queue/events` is subscribed. `connectionTimeout` is 10s. `session.onTokenReplaced` (sign-in or renewal) calls `connection.reopen()` so a renewed token is presented: a connected socket is dropped on purpose (no "Reconnecting…" shown), and if an attempt had already read the old token the new connection is dropped as soon as it is up. `parseEvent` (`lib/realtime/events.ts`) turns a frame into `message.created`, `conversation.changed`, `receipts.updated`, `unread.updated`, `typing.changed`, `presence.changed` or `ignored` (every other well-formed event: unknown kinds; garbage is dropped). `applyToList` / `applyToHistory` (`features/realtime/apply-event.ts`, pure, Vitest) put an event into the cached list and history: a Message not newer than the latest shown changes nothing (repeats and late arrivals), a Message that skips ahead is taken but asks for a refetch (list) or an `afterSeq` catch-up (history) because the unread count or the history has a hole, an unknown Conversation or `conversation.changed` refetches the list, and your own Message resets that Conversation's unread count to 0 (like the backend).  `features/realtime/sync.ts` (plain functions, Vitest with a real `QueryClient`) holds `handleEvent` and `catchUp`; the provider only wires them. **If a request for the list (or a history) is under way when an event arrives, the cache is not patched: the request is restarted instead** (invalidate), because its answer may predate the event and would undo the patch. After every (re)connection `catchUp` refetches the list (always, so even a request that began before the subscription is redone; the list is therefore requested twice at page load) and runs `catchUpHistory` (`features/messages/catch-up.ts`, `afterSeq` pages of 100) for every loaded history. `ConnectionNotice` in the signed-in header is an always-present `role=status` (`data-connection` is `connecting`, `connected` or `reconnecting`; "Reconnecting…" shows only for the last, which e2e uses as the signal that the socket is up). An open Conversation that vanishes from the list after it was shown says "You are no longer part of this Conversation." (`ConversationPane` remembers the id it showed); an id never shown stays "not found". Not done: `auth.revoked` never reaches clients (the server just closes the sockets and the reconnect succeeds while the access token lives), so a password reset elsewhere is still noticed at the next renewal; a message that arrives while the socket is being replaced is caught up on reconnect, not before. e2e: `page.routeWebSocket(/\/ws$/, …)` lets a test refuse connections (`ws.close()` in the handler), drop the current one and read the CONNECT frames (the token); jumping the clock 14 minutes also trips the client's own heartbeat check, so the renewal test proves a fresh token is presented and live again, not that `reopen()` (rather than a heartbeat reconnect) did it. A Message whose answer was lost now simply shows as sent when its live copy arrives (the pending entry is hidden by `clientMessageId`); tests that need the Retry-with-duplicate path block the socket first.
- Receipts and unread (#22, `features/receipts`): `ReceiptsProvider` (in `app/app/layout.tsx`, inside `RealtimeProvider`) owns one `createReceiptReporter` (framework-free, Vitest): `delivered(conversationId, seq)` / `read(conversationId, seq)` coalesce into one `POST /receipts` per Conversation per tick with the highest positions, never repeat a position already reported (a reported read also covers delivered), try a failed report once more after 5s (and again whenever it is asked for; a rollback only undoes the positions that report set, so a later success is not forgotten), and hand the server's answer to `recordUnread`. **Delivered** is reported (`latestFromOthers`, pure) for the latest Message from someone else in each Conversation of the list whenever the list changes (loaded at page load, or patched live by an event), so a recipient's app counts as having received it the moment it is open. **Read** is reported by `useReportReading` (used by `MessageView`): an `IntersectionObserver` over the rows of other people's Messages (`data-seq`; half of a row, or half the screen for a very long one, counts as seen) keeps the highest seen `seq`, and it is reported only while `document.visibilityState === "visible" && document.hasFocus()`, and again on the window's `focus` and `visibilitychange`; a Message scrolled below the screen is not read, so the unread count falls only as far as what was shown. The list's unread count is set by `unread.updated` (the reporter's own tabs and devices all get it, which is how two tabs agree) and by each report's response, both through `recordUnread` (`sync.ts`) and the pure `applyUnread`: a report with a lower `readSeq` than one already applied (remembered under `["read-position", id]`) is ignored, and the count is never lower than `lastMessage.seq - readSeq` for what the list already shows, so a live Message that arrived after the server counted is not lost. The sender's mark (`ReceiptMark`, a `role=img` named Sent/Delivered/Read: one dot, two dots, two dots in the accent) is `statusFor(message, frontier)`: the status the server sent with the Message, or what the **frontier** implies, whichever is further. The frontier (`receipts.updated`: the lowest of everyone else's positions, so in a Group a Message is Read only when every other Participant has read it) lives in the query cache under `["receipts", id]` (`receiptsKey`, set only by events, only ever moving forward, `useFrontier`) instead of being written into the Messages, because an event can arrive before the Message it is about. Known gaps: after a reconnect the frontier is not refetched (the history is only caught up with `afterSeq`), so a mark can stay behind until the next receipt event; a hidden tab is judged by `visibilityState` and `hasFocus()` only. e2e: `watchReports(page)` records the receipts a page sends; a test makes a page "unfocused" by an init script that replaces `document.hasFocus`; a third Participant who needs exact control reports through the backend (`deliveredUpToVia`, `readUpToVia`); on a phone the list is hidden while a Conversation is open, so tests that look at the list go back first (`showIndex`).
- Presence and typing (#23, `features/presence`): **Presence** is the generated `presenceOptions({ path: { conversationId } })` query (`usePresence`), fetched for the open Conversation only (the Direct header's `PresenceLine`, a Group's `ParticipantList` inside the header: a `<details>` "Participants (n)" with admins first, "(you)", Admin, and each other person's online dot or last seen). The server only ever lists the Conversation's other Participants, so a person you share no Conversation with is never shown. `presence.changed` events patch every loaded presence query (`allPresenceKey`, via the pure `applyPresence`: a repeat changes nothing, a last-seen time never moves backwards; a query that is being fetched is invalidated instead, like the list) and `catchUp` invalidates them after a reconnect; a `conversation.changed` event refetches that Conversation's presence (someone may have joined). `presenceText` words it ("Online", "Last seen today at 14:02", "Last seen yesterday at …", "Last seen Sun 1 Mar at …", "Offline" for never seen); the offline announcement comes about 7s after the last socket closes (grace period plus sweep), so e2e allows 25s. **Typing** is ephemeral and kept out of the query cache: `createTypingTracker` (framework-free, Vitest) holds who is typing per Conversation and forgets each person 6s after they were last heard (so a lost "stopped" or a dropped connection cannot leave "typing" stuck); `typing.changed` feeds it, a `message.created` from the typist ends their typing at once, and a (re)connection clears it. `TypingLine` (always-rendered `role=status` of fixed height above the composer) shows `typingText` ("Ada is typing", "Ada and Grace are typing", "Ada and 2 others are typing"; the dots are three `motion` spans that pulse, still under reduced motion). **Own typing** goes through `createTypingSender` (framework-free, Vitest): "typing" on the first keystroke, a reminder every 3s from then on (a timer, not tied to keystrokes, so a pause cannot let the others' 6s lapse and flicker the line), "stopped" 4s after the last keystroke, when the box is emptied, on send, and when the view closes (`stop()`, reversible so React's dev remount cannot kill it); it is published over the socket (`connection.publish` to `/app/conversations/{id}/typing`, dropped while disconnected) because the backend has no REST endpoint for it. e2e: `watchTypingSent(page)` reads a page's outgoing typing frames through `routeWebSocket`. Known limits: presence is not refetched for Conversations whose query is not loaded, only the open one is live;  presence announcements carry no timestamp for "online", so a reordered online/offline pair can leave the wrong state until the next announcement or reconnect.
- Availability (#68, GLOSSARY "Availability", backend in `docs/backend/availability.md`): `parseEvent` reads `availability.changed {userId, availability}` (only `AVAILABLE`, `BUSY`, `AWAY`; anything else is dropped). `recordAvailability` (`sync.ts`, used by the event and by the answer to the person's own change) puts it into every loaded presence query through the pure `applyAvailability` (the value already shown changes nothing) and, when it is the signed-in person's own, into `meQueryKey()`, which is how another tab's Settings moves. Presence is patched by `patchPresence`, shared with `presence.changed`: a presence query whose request is under way is cancelled and then invalidated instead (invalidating alone does not restart a *first* load, because TanStack Query only cancels a fetch that already has data; the list and histories still invalidate only). Wording (`features/presence/text.ts`): `presenceText` puts "Busy · " or "Away · " before "Online" / "Last seen …" (available adds nothing), so the Direct header's `PresenceLine` and the Group panel's `ParticipantList` both show it; the header shows no presence at all while the Conversation is blocked, and the server leaves Availability out of presence across a Block either way. `AvailabilityLine` (above `TypingLine` in `MessageView`) says "Grace is busy." / "Grace is away." in a Direct conversation that is not blocked; it is an always-present `role=status` that takes no room while empty. Settings has "Your Availability" (`features/session/availability-chooser.tsx`): a `role=radiogroup` named by the section heading, checked at the held value (`me.availability`), saved on change. Choosing the held value sends nothing; one change at a time (a choice made while one is being saved is ignored); "Availability saved." is the `role=status` (only while what was saved is still the value held); a refusal stays checked with `availabilityFailureMessage` (a 429 says how long to wait) and a "Try again" button. The UI says Available, Busy, Away and Availability, never "status" or "do not disturb". **Not exercised in a browser** (no Playwright run for this ticket): the Settings radio group (saving, the held-value no-op, the refusal and Try again, a change in another tab), the header and Group panel wording, the line above the composer and its absence while blocked. Vitest covers `parseEvent`, `applyAvailability`, `handleEvent` (every loaded presence patched, a refetch under way restarted, the own profile updated) and the wording.
