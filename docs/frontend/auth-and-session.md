# Frontend: session, routes, auth screens

Moved out of CLAUDE.md; read it before working in this area and keep it up to date.

- Session and routes (#17): the session lives in `lib/auth/session.ts` (framework-free, unit tested; `createSession({ requestTokens })`), instantiated once as `session` in `lib/auth/app-session.ts`, which also tells the API client where to read the access token (`setAccessTokenProvider`). The access token is only ever in that object's memory and `token()` returns nothing once it has run out, so an expired token is never sent (the backend would answer 401 even on public endpoints). `SessionProvider` (in the root layout) runs the silent `POST /auth/refresh` on every page load (the HttpOnly cookie travels with it; for a visitor with no cookie it is one 401 in the console); all refreshes are one in-flight request (`singleFlight`), the renewal timer fires a minute before expiry (`renewalDelayMs`), and a failed renewal of a session that existed ends it with `signedOut.ended`, which the sign-in page explains (a person who chose to sign out has `signedOut.left`, a plain visitor neither). `useSession()` reads it. `RequireSession` wraps the signed-in area (`app/app/*`, URL `/app/...`) and sends a signed-out visitor to `/sign-in?next=<path>`; `RedirectIfSignedIn` bounces signed-in people away from sign-in/sign-up; the return path is checked by `afterSignInPath` (only `/app` paths, no `..`, no other site) so a crafted `next` cannot redirect elsewhere. Signing in only starts the session (`session.signedIn`) and clears the query cache; the page redirect then does the navigation. Sign-in answers 401 with one message for a wrong password and an unknown address (`signInMessageFor`) and sends a 403 (unverified) to `/verify` with the address remembered. Sign-out is `POST /auth/logout`; only when it succeeds is the session ended and the cache cleared, otherwise the person is told they are still signed in. `GET /users/me` is `useMe()` (the first TanStack Query query, `meOptions()`). Not done: retrying a call that got 401 after a refresh (a revoked session shows up at the next renewal or on reload) and `next` keeping query strings (only the path is kept). e2e: `page.clock.install()` before signing in lets a test `fastForward` past the renewal time (the browser's timers and Date move, the server's do not), and `context.request.post(.../auth/logout)` ends the session server-side with the context's own cookie.
- Password reset (#18): `/sign-in` links to `/forgot-password` (one field; the backend answers 204 for every address and only emails verified accounts), which remembers the address (`resetEmail` in `remembered-email.ts`, sessionStorage, separate from `verificationEmail`) and goes to `/reset-password` (address, 6-digit code, new password under the usual password rules; works cold too). Everything said before the code is used is neutral so it cannot tell whether an account exists: the reset screen says "If that address has an account, we have emailed a 6-digit code" (only when the previous screen just asked for one; arriving cold it says "Enter the 6-digit code from your email…", which claims nothing), and asking for a new code says "If that address has an account, a new code is on its way". A refused code is the backend's uniform 400 (wrong, expired, too many tries), shown as "wrong or has expired" with the same client-side count of 5 as verification (`useWrongTries` / `refusedCodeMessage`, shared by both screens); asking for codes too often (429, 5 an hour per address) says when to try again via `codesMessageFor`. A successful reset ends this tab's own session too (`session.end()`, cache cleared: the backend revoked it along with all the others), then shows `PasswordChangedView` and links to sign-in. The backend revokes every refresh token and closes sockets, so a session open in another browser finds out at its next renewal (up to 14 minutes) and lands on sign-in with the "session ended" notice; there is no push to it until realtime (#21). e2e: `latestCodeFor(email, timeout, since)` only accepts an email that arrived after `since` (take `new Date()` just before asking), because an address that signed up already has an older email with a code in Mailpit; `emailCountTo` proves no email goes to an unknown address (ask about the stranger first, then wait for the known account's email, so no fixed sleep is needed).
- e2e: `waitForForm(page)` (`e2e/support/auth-screens.ts`) waits until React has taken over the form on a freshly loaded page; pressing or typing before that is handled by the browser (the form submits itself, or the typed text is thrown away), which a cold development server makes easy to hit, so tests that go straight to a sign-in or sign-up page call it first.
