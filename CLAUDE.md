# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A WhatsApp-style messenger app, as a monorepo with one git repo at the root. Domain language lives in `GLOSSARY.md`; the backend plan is GitHub issue #1 with tickets #2-#13 (see Agent skills below). The frontend is still a fresh scaffold; the backend is being built ticket by ticket.

- `backend/` — Spring Boot 4.1.x, Java 25, Maven (package `dev.salman.backend`)
- `frontend/` — Next.js 16 (App Router), React 19, Tailwind 4, TypeScript, Bun

## Backend commands (run from `backend/`)

```bash
./mvnw spring-boot:run                                  # run the app
./mvnw test                                             # all tests
./mvnw test -Dtest=BackendApplicationTests#contextLoads # single test
./mvnw package                                          # build jar
```

- `spring-boot-docker-compose` is on the classpath, so `spring-boot:run` auto-starts `compose.yaml` (Postgres, Redis, RabbitMQ, Mailpit, Grafana LGTM for OpenTelemetry). Postgres/Redis/RabbitMQ use random host ports and Spring wires them automatically; don't hardcode their URLs in dev. Mailpit is fixed at SMTP `1025` (app default) and web UI `http://localhost:8025`. Grafana is on host `3000`.
- Spring only looks for a compose file in the directory the app starts from. `./mvnw spring-boot:run` runs in `backend/` and uses `backend/compose.yaml`; running from the repo root (an IDE's default) uses the root `compose.yaml`, which just `include`s the backend one. The two start under different compose project names (`backend` and `messengerapp`), so their data volumes differ and the fixed host ports (Grafana 3000, Mailpit 1025/8025) clash if both stacks are up at once: stop one (`docker compose stop`) before starting the other.
- A stale Postgres volume from an earlier run can cause `password authentication failed for user "myuser"`; `docker compose down -v` in `backend/` fixes it.
- Tests sit at one seam: the running app's public interface. Extend `support.IntegrationTest` (MockMvc, real Postgres/Redis/RabbitMQ via `TestcontainersConfiguration`). Only email and push are faked: use the `emails` and `pushes` recording senders it exposes (e.g. read a Verification code from `emails.latestTo(...)`). `IntegrationTest.auth()` returns an `AuthClient` that drives the auth endpoints (refresh token passed and read as a cookie) from a unique client IP (so rate limits never leak between tests) and reads codes from the recorded emails. The test context uses a 4-second code TTL (`app.otp.ttl`), so code-expiry tests sleep just over 4s; token expiry is tested by moving the `MutableClock` (`clock.advance(...)`, reset before each test). `IntegrationTest` runs a real server on a random port (`port`) next to MockMvc, so `StompTestClient` can open real WebSockets; Spring's in-memory broker sends no STOMP receipts, so `RealtimeTests.listening` proves a socket is subscribed by publishing probe events through RabbitMQ until one arrives. Run the app against test containers via the `TestBackendApplication` main class.
- Schema is managed by Flyway (`spring-boot-starter-flyway`); put migrations in `src/main/resources/db/migration`. Note that JPA is also present, so don't rely on Hibernate DDL auto-generation.
- `application.yaml` holds JPA validation, virtual threads, problem details, mail host/port, and the `app.*` settings bound by `AppProperties` (JWT and OTP values are placeholders until tickets #3-#4).

## Architecture notes

Backend design (partly implemented; see issue #1 for the full spec):

- REST via `spring-boot-starter-webmvc` plus OpenAPI/Swagger UI (`springdoc-openapi`).
- Realtime: STOMP over WebSocket at `/ws` with Spring's in-memory broker per instance, and a RabbitMQ fanout exchange (`messenger.events`, one private queue per instance) carrying events between instances; see `docs/adr/0002-realtime-events-over-rabbitmq-fanout.md`. Presence lives in Redis (see below).
- Security: stateless Spring Security. Public paths are `/api/v1/auth/**`, health/info, and OpenAPI/Swagger; everything else needs a bearer JWT. Security failures are written as problem+json by `ProblemSecurityHandlers`. JWTs are self-issued (ES256, `JwtConfig`; the signing key comes from `app.jwt.private-key`/`public-key` PEMs, or an ephemeral key is generated with a warning) and validated by the resource-server filter; there is no OAuth2 client. `Clock` is a bean (`JwtConfig`) so tests can move time.
- Errors: all errors are RFC 9457 problem details with `title`, `status`, `detail`, `instance` (no `type` while it is the default). Validation failures add an `errors` map of field to message; unexpected exceptions become a generic 500. All of this lives in `GlobalExceptionHandler`; add domain exception handlers there. Security failures use the same shape via `ProblemSecurityHandlers`. Test-only `ErrorProbeController` (test classpath) exercises these paths.
- Outbound ports `EmailSender` and `NotificationSender` live in `lib`; real implementations are SMTP and (later) FCM.
- PostgreSQL is the primary store (JPA + Flyway); Lombok and MapStruct are wired via a single `annotationProcessorPaths` list in the `maven-compiler-plugin` configuration in `pom.xml` (with `lombok-mapstruct-binding`). Add any new annotation processors there. Packages are by technical layer under `dev.salman.backend` (`controller`, `service`, `repository`, `entity`, `dto`, `exception`, `config`, `lib`). **Every service is an interface in `service` with its implementation named `*Impl` in `service/impl`**; controllers and other services depend on the interface.
- Auth so far (`/api/v1/auth`): `POST signup` (202), `POST verify-email` (204), `POST resend-verification` (204). Verification codes live in Redis as an HMAC with a TTL; wrong attempts are counted per code (5 max) and sends are rate-limited per email and per client IP (fixed 1-hour window, 429 with `Retry-After`). Domain failures extend `ApiException` (an `ErrorResponseException`), which the framework renders as problem+json. Emails are normalized (trimmed, lower-cased) in the request records via `Emails.normalize`. Reuse the composed constraints `@ValidEmail`, `@ValidPassword` (8-72 characters and at most 72 UTF-8 bytes because of BCrypt) and `@ValidVerificationCode` on request fields. Free text goes through `@ValidDisplayName`, `@ValidGroupName` and `@ValidMessageBody` (all built on `TextRules`: not blank, a maximum counted in Unicode code points like PostgreSQL, no NUL, which PostgreSQL cannot store); use that for any new text column rather than `@Size`. Controllers get the signed-in User's id from `Principals.userId(jwt)`.
- Password reset (`/api/v1/auth`): `POST forgot-password` (204 for any email; only verified Users are actually emailed; counts against the same hourly send limits as sign-up) and `POST reset-password` (`email`, `code`, `newPassword`; 204). Reset codes use their own `Purpose.PASSWORD_RESET` key space in `VerificationCodeService`, so they are not interchangeable with email-verification codes. A successful reset hashes the new password first, then (holding the User row lock) consumes the code, changes the password and deletes every refresh-token family in one transaction; already-issued access tokens stay valid until they expire. **Sign-in, refresh and reset all take `UserRepository.findBy...ForUpdate`**, so a session can never be created from a password a concurrent reset just replaced; keep taking that lock in any new code that creates sessions or changes credentials. Code emails are sent on the `mailExecutor` (virtual threads) and failures are only logged, so responses and timing never reveal whether an address has an account; tests swap in a same-thread executor and can make sends fail with `emails.failFor(address)`.
- User lookup: `POST /api/v1/users/lookup` with `{"email": ...}` (authenticated; POST so the address stays out of URLs and logs) returns `{id, displayName}` for an exact, case-insensitive match of a verified User and a 404 problem with an identical body for everything else (unknown, unverified, partial, wildcard). It is deliberately not a search; other Users never see an email or verification state, and the request deliberately skips `@ValidEmail` so odd input is a miss, not a different error. Each call, found or not, counts against a per-caller allowance (`app.lookup.max-per-minute`, default 30; 429 with `Retry-After`). Throttling goes through the shared `RateLimiter` service (fixed window, one Lua script); use it for any new limit. A Flyway check constraint refuses stored emails containing A-Z, so keep normalizing in code before every write.
- Conversations (`/api/v1/conversations`): `POST direct` with `{"userId"}` starts a Direct conversation with a verified User and returns 201, or 200 with the same body if the pair already has one (whoever starts it); yourself is a 400, an unknown or unverified User a 404. `GET` lists the caller's Conversations, most recently active (`updated_at`) first, with their participants' ids, display names and roles. Schema (`V3`): `conversation` (type DIRECT/GROUP, `direct_key` = both User ids sorted and joined by `:`, unique and required exactly for DIRECT, `last_seq` for message ordering, `updated_at` for list order) and `participant` (unique per conversation and user). Creating a Direct conversation takes a transaction-scoped Postgres advisory lock on the key (`ConversationRepository.lockDirectKey`), so concurrent creators serialise; the unique constraint is only the backstop. Responses are built with three queries per list, not per conversation. `lastMessage` is the latest Message the viewer may read (null until one is sent) and `unreadCount` is `last_seq - the viewer's last_read_seq`.
- Messages (`/api/v1/conversations/{id}/messages`, see `docs/adr/0001-server-assigned-message-sequence.md`): `POST` `{clientMessageId, body}` (body validated by `@ValidMessageBody`: not blank, at most 4000 characters counted as Unicode code points like the database check, no NUL; stored exactly as sent) returns 201 with the stored Message `{id, conversationId, seq, senderId, clientMessageId, body, createdAt}`, or 200 with the same Message when that sender already used the `clientMessageId` in that conversation with the same text (409 if the text differs). `seq` comes from `conversation.last_seq`, incremented while holding `ConversationRepository.findByIdForUpdate`, so it is gap-free and concurrent sends and retries serialise per conversation; keep that lock for anything that writes Messages. `GET` returns `{messages, hasMore}` in ascending `seq`: newest `limit` (default 50, max 100) by default, `beforeSeq` pages back, `afterSeq` catches up (not both). A non-participant and an unknown conversation get the same 404. Message `createdAt`/`updated_at` use the microsecond `Clock` bean (Postgres precision) so a value reads back exactly as written. Sending moves the conversation to the top of the list by bumping `updated_at`. Row locks never wait forever: `spring.datasource.hikari.connection-init-sql` sets `lock_timeout` (5s; tests use 1.5s), and a wait that times out becomes a 503 problem with `Retry-After` in `GlobalExceptionHandler`. The history endpoint checks membership before anything else, so a non-participant only ever sees the uniform 404. Membership is checked again under the conversation lock, so a send queued behind a removal is refused. A Participant reads only Messages after `participant.joined_after_seq` (set to the conversation's `last_seq` when they join; history, paging and `lastMessage` all respect it). Not done yet: a send throttle and a request-body size cap.
- Groups (`/api/v1/conversations`, `GroupService`): `POST groups` `{name, userIds}` (name 1-100 characters; 1-255 other verified Users, duplicates and yourself ignored, any unknown or unverified one is a 404 for the whole request) makes the caller ADMIN and the rest MEMBER; `PATCH /{id}` `{name}` renames; `POST /{id}/participants` `{userId}` adds (409 if already in or the group has 256); `DELETE /{id}/participants/{userId}` removes (not yourself: 400, use leave); `POST /{id}/participants/{userId}/promote` makes an ADMIN (idempotent); `POST /{id}/leave`; `GET /{id}` returns one conversation. Admin-only changes give a Participant who is not an admin a 403, a non-participant the uniform 404, and a Direct conversation a 400. Every change takes `ConversationRepository.findByIdForUpdate` and reads the caller's membership again under it. When the last admin leaves, the earliest-joined remaining Participant (ties by user id) becomes admin; when the last Participant leaves the conversation row is deleted and the database cascades to participants and messages. Adding someone back after removal starts a fresh join point. Creating groups is throttled per User (`app.groups.max-created-per-hour`, default 20, failed attempts count, 429 with `Retry-After`). `participants` are listed admins first, then by join time. Responses are built by the package-private `ConversationAssembler` for a given viewer; the join-point rule lives on `Participant` (`canRead`, `readableAfter`). A removed sender's old messages stay, but their name is no longer in `participants` (messages carry only `senderId`).
- Receipts (`POST /api/v1/conversations/{id}/receipts` `{deliveredSeq?, readSeq?}`, `ReceiptService`; see GLOSSARY): each Participant has `last_delivered_seq` and `last_read_seq` (migration `V6`, constraint `joined_after_seq <= read <= delivered`; both start at the join point so pre-join history is never unread). Reports move positions forward only, atomically, with `ParticipantRepository.advanceReceipts` (one `greatest(...)` UPDATE, no conversation lock needed because `last_seq` only grows); a lower or late report is ignored with a 200, reading counts as delivering, a position beyond `last_seq` is a 400, and a non-participant gets the uniform 404. Sending advances the sender's own positions to the new Message, so a reply marks everything before it as read (deliberate, like common chat apps; a product decision to revisit if wanted). A Message's `status` (`SENT`/`DELIVERED`/`READ`, `MessageStatuses`) is set only for its sender and is the minimum of the other Participants' positions (a later joiner can't lower it because their positions start at their join point; with nobody else left it stays `SENT`). It appears on the send response, history pages and the list's `lastMessage`. `Participant` is `@DynamicUpdate` so changing a loaded copy (e.g. a role) can never write stale positions back over the atomic `advanceReceipts` update; keep it that way, and use `Participant.unreadCount(lastSeq)` for the definition. A new Message's status is always `SENT` (nobody can have reported it yet); a retry computes the current status. Positions are reported by clients; nothing marks messages delivered automatically yet (realtime, #11).
- Realtime (#11): the HTTP handshake at `/ws` is public (browsers cannot set headers on it); the access token goes in the STOMP `CONNECT` frame's `Authorization: Bearer` header and `StompAuthInterceptor` checks it (valid, User still exists and is verified). A bad or missing token, a disallowed destination or any frame after the token expired gets an ERROR frame and the socket is closed shortly after (`StompSessions.closeSoon`); `StompSessions.closeExpired()` (every 10s) closes idle sockets whose token expired, and a password reset closes all of that User's sockets on every instance (the `auth.revoked` control event; logout cannot, because sockets are not tied to refresh sessions), so a socket is never a longer revocation gap than REST (up to 15 minutes). A second CONNECT on a session is refused (Spring also answers it with an ERROR). Sockets that never authenticate need no sweep: Spring closes ones that send nothing or only heartbeats. Clients may only subscribe to `/user/queue/events` and `/user/queue/errors` and only send to `/app/conversations/{id}/receipts` (same payload as the REST receipts endpoint) and `/app/conversations/{id}/typing` (the id must be a real UUID; problems come back on the error queue as `{type:"error", status, title, detail, errors?}`). Events are pushed to users, never to conversations: `RealtimeEvents` works out the recipients from the CURRENT participants when the change happens, publishes after the transaction commits (`RealtimePublisher` -> fanout exchange -> `RealtimeListener` on every instance -> `convertAndSendToUser`), so removed or departed Participants stop hearing about a conversation immediately. Event `type`s: `message.created` (`message`, no status), `receipts.updated` (`deliveredUpTo`, `readUpTo`: the `ReceiptFrontier` of everyone else, per recipient; only sent to recipients for whom it actually moved, including when a reply moves the sender's own positions), `unread.updated` (the reporter's own `deliveredSeq`, `readSeq`, `unreadCount`, to the reporter only) and `conversation.changed` (refetch it; also sent to people who just left or were removed). Events are best effort and may arrive out of order: clients order messages by `seq`, treat frontiers as increasing, and refetch and catch up with `afterSeq` after any reconnect (see ADR 0002). The infrastructure components `StompSessions`, `StompAuthInterceptor` and `RealtimeListener` are adapters in `lib`, not services, so they have no interface; services (`RealtimeEvents`) still do. Frames are limited to 16 KB. Not done: automatic delivered marking, rate limits on socket frames.
- Presence and typing (#12): a User is online while any socket of theirs has a live entry in Redis (`presence:sockets:{user}`, a sorted set of socket ids scored by when each lapses, plus `presence:announced:{user}`; all transitions are Lua scripts in `PresenceServiceImpl`, times from the `Clock` bean). `PresenceListener` marks a socket connected/disconnected from Spring's `SessionConnectedEvent`/`SessionDisconnectEvent`; `PresenceHeartbeat` refreshes this instance's live sockets every 10s (one call per User) and an entry lapses after `app.presence.ttl` (30s). **Offline is decided by a sweep, never by an in-memory timer**: the shared sorted set `presence:watch` holds every User who may need to go offline, scored by when they are expected to have no socket (the disconnect time, or the latest lapse time), and every instance runs `PresenceService.sweep()` every `app.presence.sweep-interval` (2s). A User quiet for longer than `app.presence.offline-grace` (5s, tests 1s) is claimed atomically with a lease (`presence:claimed` keeps the original time), their `users.last_seen_at` is stored, `presence.changed {online:false, lastSeenAt}` is announced and the claim is released; if that fails the lease lapses and a later sweep retries (at least once, so clients treat a repeat as no change). So a restart, a crash, a heartbeat landing after a disconnect or a dead instance all end in an announcement. The first socket announces `presence.changed {userId, online:true}` (if publishing fails the flag is cleared so the next heartbeat retries). `last_seen_at` is also written the moment the last socket closes, and only ever moves forward (`UserRepository.updateLastSeen`); `GET` reports offline (with that last seen) from that moment even though the offline announcement waits out the grace period. Instances should run time sync, because entries are scored with each instance's clock. Announcements go to everyone who shares any conversation with the User (`ParticipantRepository.findCoParticipantIds`), online or not, so a user in many large groups produces a long recipient list: revisit if that grows. `GET /api/v1/conversations/{id}/presence` lists the OTHER participants' `{userId, online, lastSeenAt}` (`lastSeenAt` only while offline); participants only, uniform 404 otherwise. Typing: `SEND /app/conversations/{id}/typing {typing: bool}` -> `typing.changed {conversationId, userId, typing}` to the other current participants, never stored; starts are limited to 10 per 10s per user and conversation and stops to 30 (excess dropped silently); clients should treat a start as stale after a few seconds. `User` is `@DynamicUpdate` (like `Participant`) so a loaded copy can never write an old `last_seen_at` back. Socket errors for all inbound messages are rendered by the `SocketErrors` advice.
- Push (#13): `POST /api/v1/devices` `{token, platform: ANDROID|IOS|WEB}` registers a device (201; 200 and nothing changes if the caller already has the token; 409 beyond `app.push.max-devices-per-user`, 10) and returns `{id, platform, createdAt}`, never the token; `DELETE /api/v1/devices/{id}` is 204 whether or not it existed and only ever removes the caller's own. **A token another User had moves to the caller** (deliberate: the same phone legitimately changes accounts; the token is a secret only that phone's app knows). Tokens go through `@ValidDeviceToken` (4096 max, no NUL; registration takes an advisory lock on the token like Direct conversations do on their key). A password reset deletes every device of the User, and `POST /auth/logout` takes an optional body `{deviceId}` that deletes that device when it belongs to the session being logged out (the refresh cookie proves who that is). Sending a new Message (`MessageServiceImpl`, never a retried one) calls `PushService.messageStored`, which after commit (`AfterCommit.run`, shared with `RealtimeEventsImpl`) only queues a `PushJob` on `messenger.push.messages` (durable, default exchange; a publish failure is logged and never fails the send; there is no outbox, so a broker outage at that instant loses that Message's push). `PushListener` (lib) runs two workers. `PushService.fanOut` takes the CURRENT participants except the sender, drops those with a live socket (`PresenceService.onlineAmong`) and queues one `PushDelivery {deviceId, userId, token, title, body, attempt}` per device on `messenger.push.deliveries`, each device at most once per Message (Redis `SET NX push:queued:{messageId}:{deviceId}`, 1 day, undone if the publish fails); title is the sender's display name (in a Group `Name in Group`), body the first 100 characters plus an ellipsis. If fan-out fails the whole job is retried through `messenger.push.messages.retry`. `PushService.deliver` sends through the `NotificationSender` port, which returns `DELIVERED` or `TOKEN_REJECTED` (the registration that was queued, matched by token AND the queued `userId`, is deleted, so a token that has since moved is untouched) or throws `PushUnavailableException`, the only thing retried (via `messenger.push.retry`). Retry queues dead-letter back to their work queue after `app.push.retry-delay` (30s; tests 500ms) so a retry never blocks a worker; after `app.push.max-attempts` (5), or when even queueing a retry fails, the work is parked on `messenger.push.dead` (nothing consumes it; header `kind` is `job` or `delivery`; it holds the preview text and token, so protect it like the other queues). Any other exception from the provider call is logged and dropped. If even parking fails the exception leaves the listener and the broker requeues the message; only unreadable messages are dropped. `FcmNotificationSender` is only active when `app.push.fcm.credentials-file` (env `FCM_CREDENTIALS_FILE`) is set (FCM `UNREGISTERED`, `INVALID_ARGUMENT` and `SENDER_ID_MISMATCH` mean rejected, everything else temporary; `INVALID_ARGUMENT` can also mean a bad payload, so a payload bug could delete devices); otherwise `LoggingNotificationSender` logs only the title. It has no automated test since it needs real credentials. Tests use `pushes` (`RecordingNotificationSender`: `failNext(n)`, `breakNext(e)`, `reject(token)`, `attempts()`, `all()`) and `pushQueue` (`FaultyPushPublisher`, the real publisher with broker-outage switches). Not done: an outbox for the publish after commit, collapsing several pushes into one per conversation, per-conversation mute or a way to hide the preview, badge counts, pushing other event kinds, purging devices of users who never come back, re-checking at registration that the User still exists, and online status is checked when the worker runs, not when the Message was stored.
- Sessions (`/api/v1/auth`): `POST login` (200 with `accessToken`, `tokenType`, `expiresIn` in the body; 401 for unknown email or wrong password with an identical message, 403 only when the password is right but the email is unverified), `POST refresh`, `POST logout` (204, idempotent; optional body `{deviceId}` to stop push to that device), and `GET /api/v1/users/me`. Access tokens last 15 minutes and are stateless (they stay valid after logout until they expire, and only `/users/me` re-checks the user exists). **The refresh token is never in a response body**: it is an `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth` cookie named `refresh_token` (`RefreshCookies`; `app.refresh-cookie.secure` (env `REFRESH_COOKIE_SECURE`) can be false for plain-HTTP dev; Chrome and Firefox accept Secure cookies on `http://localhost` anyway, Safari does not). `/refresh` and `/logout` read it from the cookie (no request body), a rotated cookie is set on every refresh, and a failed refresh or any logout clears it. Refresh tokens are opaque, single-use, stored as SHA-256, grouped in a family per login; using a used one deletes its family (transaction uses `noRollbackFor = ApiException`); logout deletes the family. Used/expired refresh rows are not yet purged. CSRF protection stays disabled because endpoints authenticate with the bearer header; the cookie is protected by SameSite=Strict plus `CorsConfig`, which rejects cross-origin requests from any origin not in `app.cors.allowed-origins` (default `http://localhost:3000` and `http://localhost:3001`, the latter for `bun dev -p 3001` next to Grafana; override with `APP_CORS_ALLOWED_ORIGINS`). Requests with no `Origin` header (mobile apps, curl) are allowed.
