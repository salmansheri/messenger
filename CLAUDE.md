# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A WhatsApp-style messenger app, as a monorepo with one git repo at the root. Domain language lives in `GLOSSARY.md`; the backend plan is GitHub issue #1 with tickets #2-#13 (see Agent skills below). The backend is finished (tickets #2-#13); the frontend is being built from the spec in issue #14 and its tickets #15-#25.

- `backend/` — Spring Boot 4.1.x, Java 25, Maven (package `dev.salman.backend`)
- `frontend/` — Next.js 16 (App Router), React 19, Tailwind 4, TypeScript, Bun

## Backend commands (run from `backend/`)

```bash
./mvnw spring-boot:run                                  # run the app
./mvnw test                                             # all tests
./mvnw test -Dtest=BackendApplicationTests#contextLoads # single test
./mvnw package                                          # build jar
```

- `spring-boot-docker-compose` is on the classpath, so `spring-boot:run` auto-starts `compose.yaml` (Postgres, Redis, RabbitMQ, Mailpit, Grafana LGTM for OpenTelemetry). Redis/RabbitMQ use random host ports and Spring wires them automatically; don't hardcode their URLs in dev. Postgres is pinned to host port `5433` so a database client (DBeaver) keeps working across restarts: `jdbc:postgresql://localhost:5433/mydatabase`, user `myuser`, password `secret`. The root and backend compose stacks would clash on it if both were up at once, like Grafana and Mailpit. Mailpit is fixed at SMTP `1025` (app default) and web UI `http://localhost:8025`. Grafana is on host `3000`.
- Spring only looks for a compose file in the directory the app starts from. `./mvnw spring-boot:run` runs in `backend/` and uses `backend/compose.yaml`; running from the repo root (an IDE's default) uses the root `compose.yaml`, which just `include`s the backend one. The two start under different compose project names (`backend` and `messengerapp`), so their data volumes differ and the fixed host ports (Grafana 3000, Mailpit 1025/8025) clash if both stacks are up at once: stop one (`docker compose stop`) before starting the other.
- A stale Postgres volume from an earlier run can cause `password authentication failed for user "myuser"`; `docker compose down -v` in `backend/` fixes it.
- Tests sit at one seam: the running app's public interface. Extend `support.IntegrationTest` (MockMvc, real Postgres/Redis/RabbitMQ via `TestcontainersConfiguration`). Only email and push are faked: use the `emails` and `pushes` recording senders it exposes (e.g. read a Verification code from `emails.latestTo(...)`). `IntegrationTest.auth()` returns an `AuthClient` that drives the auth endpoints (refresh token passed and read as a cookie) from a unique client IP (so rate limits never leak between tests) and reads codes from the recorded emails. The test context uses a 4-second code TTL (`app.otp.ttl`), so code-expiry tests sleep just over 4s; token expiry is tested by moving the `MutableClock` (`clock.advance(...)`, reset before each test). `IntegrationTest` runs a real server on a random port (`port`) next to MockMvc, so `StompTestClient` can open real WebSockets; Spring's in-memory broker sends no STOMP receipts, so `RealtimeTests.listening` proves a socket is subscribed by publishing probe events through RabbitMQ until one arrives. Run the app against test containers via the `TestBackendApplication` main class.
- Schema is managed by Flyway (`spring-boot-starter-flyway`); put migrations in `src/main/resources/db/migration`. Note that JPA is also present, so don't rely on Hibernate DDL auto-generation.
- `application.yaml` holds JPA validation, virtual threads, problem details, mail host/port, and the `app.*` settings bound by `AppProperties` (JWT and OTP values are placeholders until tickets #3-#4).

## Frontend commands (run from `frontend/`)

```bash
bun dev           # dev server (Turbopack) on port 3001, because 3000 is Grafana's
bun run build
bun run lint      # eslint (generated API code is ignored)
bun run typecheck # tsc --noEmit
bun run test      # Vitest: pure modules only (lib/**, features/**, *.test.ts)
bun run e2e       # Playwright against the real backend, desktop and phone projects
bun run api       # regenerate lib/api/generated from the running backend's /v3/api-docs
```

- **Next.js 16 has breaking changes from older versions.** `frontend/AGENTS.md` requires reading the relevant guide in `frontend/node_modules/next/dist/docs/` before writing Next.js code. Heed deprecation notices. `next.config.ts` enables `cacheComponents` and partial prefetching: reading `cookies()` or other request data in a layout makes everything under it dynamic, which is why the theme cookie is read by an inline script instead (see below).
- If styles or the theme look wrong after editing CSS in odd ways (or after `bun run build`), delete `frontend/.next`: the dev server's cache can go stale and make e2e tests fail for no code reason.
- The root `.mcp.json` registers `next-devtools-mcp`; use it for Next.js runtime/docs queries when available.
- Port clash: the Grafana LGTM container in the backend compose file maps host port `3000`, the same as `next dev`'s default, so the `dev` script already uses `3001` (the backend allows both origins).
- Playwright's `webServer` starts the backend (`./mvnw spring-boot:run` in `backend/`, which brings up the compose stack incl. Mailpit) and the frontend as a **production build on its own port, 3002** (`bun run build && next start -p 3002`, built into `.next-e2e` through `NEXT_DIST_DIR`, fresh every run, never reusing a server that is already there), so the suite neither depends on nor disturbs the development server on 3001 that you may be starting and stopping; the backend is given `APP_CORS_ALLOWED_ORIGINS` for that origin (`FRONTEND_URL` in `e2e/playwright-urls.ts`). `E2E_DEV=1` serves `next dev -p 3002` instead for quick iteration, at the price of cold-compile slowness and flakes. Every test runs in four projects: `desktop-light`, `desktop-dark`, `phone-light`, `phone-dark` (the app follows the system colour scheme by default, which each project sets; `openSession()` contexts inherit it), so the whole suite takes about ten minutes and tests that look at the project name use `startsWith("desktop")` / `startsWith("phone")`. It **refuses to adopt a running backend** (it would spend that backend's real throttle allowance and leave test data in it): stop your backend before `bun run e2e`, or set `E2E_REUSE_SERVERS=1` if you started it yourself with the raised limits below. It raises the backend's per-IP, lookup and group throttles through `APP_OTP_MAX_SENDS_PER_IP_PER_HOUR`, `APP_LOOKUP_*` and `APP_GROUPS_*` environment variables (the per-email code limit stays at 5 an hour because a test exercises it, so use a fresh email per test); if you start the backend yourself, pass the same ones or a long suite will meet 429s. Test data is never cleaned up; every test uses unique emails. `e2e/support` has the `openSession()` fixture (a page in a fresh browser context, for tests with several people) and `createVerifiedAccount()` (signs up and verifies through the backend, reading the code from Mailpit's REST API at `localhost:8025`) and `signIn()`.
- Frontend tests sit at one seam (see issue #14): the running app in a real browser against the real backend, nothing mocked. **One recorded exception: failure injection at the network edge.** A test may use `page.route` / `page.routeWebSocket` to make a request fail, answer 429 or 503, hold an answer back, lose an answer, or refuse a socket, because the real backend cannot produce those on demand (a 503, a throttle that is deliberately raised in tests, a response that never arrives). The app and the backend stay real, the injected answer is the one the backend itself would give (a problem+json with the real CORS headers and `Retry-After`), and a test never fakes a success or a body the backend would not send. Anything else that needs the backend uses the backend. Vitest is only for pure modules a browser cannot reach cheaply (token single-flight, optimistic-send state machine, event reducer, Zod schemas, theme and problem parsing).

## Architecture notes

Backend design (partly implemented; see issue #1 for the full spec):

- REST via `spring-boot-starter-webmvc` plus OpenAPI/Swagger UI (`springdoc-openapi`).
- Realtime: STOMP over WebSocket at `/ws` with Spring's in-memory broker per instance, and a RabbitMQ fanout exchange (`messenger.events`, one private queue per instance) carrying events between instances; see `docs/adr/0002-realtime-events-over-rabbitmq-fanout.md`. Presence lives in Redis (see below).
- Security: stateless Spring Security. Public paths are `/api/v1/auth/**`, health/info, and OpenAPI/Swagger; everything else needs a bearer JWT. Security failures are written as problem+json by `ProblemSecurityHandlers`. JWTs are self-issued (ES256, `JwtConfig`; the signing key comes from `app.jwt.private-key`/`public-key` PEMs, or an ephemeral key is generated with a warning) and validated by the resource-server filter; there is no OAuth2 client. `Clock` is a bean (`JwtConfig`) so tests can move time.
- Errors: all errors are RFC 9457 problem details with `title`, `status`, `detail`, `instance` (no `type` while it is the default). Validation failures add an `errors` map of field to message; unexpected exceptions become a generic 500. All of this lives in `GlobalExceptionHandler`; add domain exception handlers there. Security failures use the same shape via `ProblemSecurityHandlers`. Test-only `ErrorProbeController` (test classpath) exercises these paths.
- Outbound ports `EmailSender` and `NotificationSender` live in `lib`; real implementations are SMTP and (later) FCM.
- PostgreSQL is the primary store (JPA + Flyway); Lombok and MapStruct are wired via a single `annotationProcessorPaths` list in the `maven-compiler-plugin` configuration in `pom.xml` (with `lombok-mapstruct-binding`). Add any new annotation processors there. Packages are by technical layer under `dev.salman.backend` (`controller`, `service`, `repository`, `entity`, `dto`, `exception`, `config`, `lib`). **Every service is an interface in `service` with its implementation named `*Impl` in `service/impl`**; controllers and other services depend on the interface.
- Auth so far (`/api/v1/auth`): `POST signup` (202), `POST verify-email` (204), `POST resend-verification` (204). Verification codes live in Redis as an HMAC with a TTL; wrong attempts are counted per code (5 max) and sends are rate-limited per email and per client IP (fixed 1-hour window, 429 with `Retry-After`). Domain failures extend `ApiException` (an `ErrorResponseException`), which the framework renders as problem+json. Emails are normalized (trimmed, lower-cased) in the request records via `Emails.normalize`. Reuse the composed constraints `@ValidEmail`, `@ValidPassword` (8-72 characters and at most 72 UTF-8 bytes because of BCrypt) and `@ValidVerificationCode` on request fields. Free text goes through `@ValidDisplayName`, `@ValidGroupName` and `@ValidMessageBody` (all built on `TextRules`: not blank, a maximum counted in Unicode code points like PostgreSQL, no NUL, which PostgreSQL cannot store); use that for any new text column rather than `@Size`. Controllers get the signed-in User's id from `Principals.userId(jwt)`.
- Password reset (`/api/v1/auth`): `POST forgot-password` (204 for any email; only verified Users are actually emailed; counts against the same hourly send limits as sign-up) and `POST reset-password` (`email`, `code`, `newPassword`; 204). Reset codes use their own `Purpose.PASSWORD_RESET` key space in `VerificationCodeService`, so they are not interchangeable with email-verification codes. A successful reset hashes the new password first, then (holding the User row lock) consumes the code, changes the password and deletes every refresh-token family in one transaction; already-issued access tokens stay valid until they expire. **Sign-in, refresh and reset all take `UserRepository.findBy...ForUpdate`**, so a session can never be created from a password a concurrent reset just replaced; keep taking that lock in any new code that creates sessions or changes credentials. Code emails are sent on the `mailExecutor` (virtual threads) and failures are only logged, so responses and timing never reveal whether an address has an account; tests swap in a same-thread executor and can make sends fail with `emails.failFor(address)`.
- User lookup: `POST /api/v1/users/lookup` with `{"email": ...}` (authenticated; POST so the address stays out of URLs and logs) returns `{id, displayName}` for an exact, case-insensitive match of a verified User and a 404 problem with an identical body for everything else (unknown, unverified, partial, wildcard). It is deliberately not a search; other Users never see an email or verification state, and the request deliberately skips `@ValidEmail` so odd input is a miss, not a different error. Each call, found or not, counts against a per-caller allowance (`app.lookup.max-per-minute`, default 30; 429 with `Retry-After`). Throttling goes through the shared `RateLimiter` service (fixed window, one Lua script); use it for any new limit. A Flyway check constraint refuses stored emails containing A-Z, so keep normalizing in code before every write.
- Conversations (`/api/v1/conversations`): `POST direct` with `{"userId"}` starts a Direct conversation with a verified User and returns 201, or 200 with the same body if the pair already has one (whoever starts it); yourself is a 400, an unknown or unverified User a 404. `GET` lists the caller's Conversations, most recently active (`updated_at`) first, with their participants' ids, display names and roles. Schema (`V3`): `conversation` (type DIRECT/GROUP, `direct_key` = both User ids sorted and joined by `:`, unique and required exactly for DIRECT, `last_seq` for message ordering, `updated_at` for list order) and `participant` (unique per conversation and user). Creating a Direct conversation takes a transaction-scoped Postgres advisory lock on the key (`ConversationRepository.lockDirectKey`), so concurrent creators serialise; the unique constraint is only the backstop. Responses are built with three queries per list, not per conversation. `lastMessage` is the latest Message the viewer may read (null until one is sent) and `unreadCount` is `last_seq - the viewer's last_read_seq`.
- Messages (`/api/v1/conversations/{id}/messages`, see `docs/adr/0001-server-assigned-message-sequence.md`): `POST` `{clientMessageId, body}` (body validated by `@ValidMessageBody`: not blank, at most 4000 characters counted as Unicode code points like the database check, no NUL; stored exactly as sent) returns 201 with the stored Message `{id, conversationId, seq, senderId, clientMessageId, body, createdAt}`, or 200 with the same Message when that sender already used the `clientMessageId` in that conversation with the same text (409 if the text differs). `seq` comes from `conversation.last_seq`, incremented while holding `ConversationRepository.findByIdForUpdate`, so it is gap-free and concurrent sends and retries serialise per conversation; keep that lock for anything that writes Messages. `GET` returns `{messages, hasMore}` in ascending `seq`: newest `limit` (default 50, max 100) by default, `beforeSeq` pages back, `afterSeq` catches up (not both). A non-participant and an unknown conversation get the same 404. Message `createdAt`/`updated_at` use the microsecond `Clock` bean (Postgres precision) so a value reads back exactly as written. Sending moves the conversation to the top of the list by bumping `updated_at`. Row locks never wait forever: `spring.datasource.hikari.connection-init-sql` sets `lock_timeout` (5s; tests use 1.5s), and a wait that times out becomes a 503 problem with `Retry-After` in `GlobalExceptionHandler`. The history endpoint checks membership before anything else, so a non-participant only ever sees the uniform 404. Membership is checked again under the conversation lock, so a send queued behind a removal is refused. A Participant reads only Messages after `participant.joined_after_seq` (set to the conversation's `last_seq` when they join; history, paging and `lastMessage` all respect it). Sending is throttled per User through `MessageThrottle` (`app.messages.max-sends-per-minute`, default 60, across all Conversations; 429 with `Retry-After`): it is counted before the conversation lock is taken (an over-limit User never queues for it) and only when no stored copy of the Message exists, so a retry the server already answered (200) never counts, and a refused send stores nothing (no gap in `seq`); like the other limits it is spent even if the send then fails for another reason; the counter is a fixed Redis window, so a test cannot move it with the `Clock` and the window's expiry is not tested here. `MessageThrottle.change` is the separate allowance for edits, deletions and reactions (`app.messages.max-changes-per-minute`, 120), unused until those exist; tests reach it through the test-only `ErrorProbeController`. Not done yet: a request-body size cap.
- Edit and delete (#28, see `docs/adr/0004-deleted-messages-keep-their-place.md`): `PATCH /{id}/messages/{messageId}` `{body}` edits the caller's own Message (`@ValidMessageBody`; `app.messages.edit-window`, 15 minutes after `createdAt`; sets `editedAt`, keeps no earlier text; the same text changes nothing and sends no event), `DELETE /{id}/messages/{messageId}` deletes it for everyone (204; `app.messages.delete-window`, 1 hour; repeating it is a 204 that changes nothing, even after the window) and `POST /{id}/messages/{messageId}/hide` hides any readable Message from the caller's own view only (204, no window, repeatable). A Message deleted for everyone keeps its row, `seq`, sender and time with `body` null and `deletedAt` set (a check constraint ties the two), so it is a placeholder in history, paging, catch-up and `lastMessage`. Message responses gained `editedAt` and `deletedAt`. Rules: only the sender may edit or delete for everyone (403 for anyone else who can read the Message; Admins get no extra right); a non-participant, an unknown Message, one from another Conversation and one from before the caller joined are all the same 404; a closed window or editing a deleted Message is a 409 with its own wording; edit and delete take the conversation lock and read membership again under it, so a removal queued first wins. Edits and deletions change no `seq`, receipts, status, unread count, `updated_at` order or push (`PushService` skips a Message deleted before the worker ran). `MessageThrottle.change` is counted for edit, delete and hide (before the lock), sharing the 120-a-minute allowance. Hiding is a row in `message_hidden`; history, `beforeSeq` paging and `afterSeq` catch-up filter hidden Messages in the query (`findVisible…`), so pages stay full, and `lastMessage` falls back to the latest Message the viewer has not hidden (null if they hid all). **Decision: `unreadCount` stays plain Sequence arithmetic**, so a Message hidden before it was read still counts until the read position passes it (a hidden last Message can keep the count above zero until the next Message; the frontend ticket decides how to handle that). Hiding sends no event, so a person's other tabs find out at their next fetch. Event `message.updated` (`message` with `body` or `deletedAt`, and `editedAt`; no `status`) goes to the CURRENT Participants after commit, only when something changed. A retry of the send of an edited or deleted Message (same Client message ID) answers 200 with the stored Message whatever text it carries, because the original text is gone. `message.updated` skips people who joined after the Message and people who hid it. **Known limits**: `afterSeq` catch-up only returns Messages with a higher `seq`, so a client that missed `message.updated` (a dropped socket) never learns of an edit or deletion that way: the frontend must refetch its loaded history pages after a reconnect (a cursor such as `updatedAfter` was left out on purpose); a push already queued or being retried keeps the preview text it was queued with even if the Message is deleted afterwards (the guard only covers a job that has not fanned out yet); `lastMessage` costs one extra query per Conversation whose latest Message the viewer hid; an edit that changes nothing and a repeated delete still use the change allowance. Tests: `EditDeleteMessageTests` (move the clock past the windows and take a fresh token with `loginForTokens`, since tokens last 15 minutes) and `MessageUpdatedEventTests`.
- Mute, archive and pin (#29, `ConversationSettingsService`): `PATCH /api/v1/conversations/{id}/settings` `{mute?: NONE|EIGHT_HOURS|ONE_WEEK|ALWAYS, archived?, pinned?}` changes only what is present and returns the Conversation as the caller sees it (an empty body, or archived and pinned both true, is a 400; a non-participant gets the uniform 404). The settings are columns on `participant` (`muted_until`, `muted_forever`, `archived`, `pinned`; migration `V9`, with a check that a Conversation is never archived and pinned), so they are private to their owner and **leaving or being removed clears them** (re-adding starts with the defaults). Every `ConversationResponse` carries the viewer's own `settings {muted, mutedUntil, archived, pinned}`: `muted` without `mutedUntil` is muted for ever, a mute that has run out simply reads as not muted (there is no job and no event at expiry; clients compute from `mutedUntil`). Mute only silences push: `PushServiceImpl.queueDeliveries` skips recipients muted at the moment the worker runs (the `Clock` bean), while unread counts and live events are untouched. Archiving never undoes itself when a Message arrives; archiving a pinned Conversation unpins it (one request); pinning an archived one is a 409 "Unarchive it before pinning." (unarchive and pin in one request is fine); a fourth pin is a 409 "You can pin at most 3 Conversations."; all settings changes of one User are serialised with an advisory lock taken before the participant row is read (`ParticipantRepository.lockPinsOf`), so concurrent pins respect the limit and concurrent archive and pin never act on a stale row; the check constraint is only the backstop. `GET /conversations` lists pinned Conversations first and the rest by recent activity (the pinned ones keep that order among themselves); the Archived view is the frontend's filter on `settings.archived`, the server does not split the list. `settings.changed` (`settings`) goes to the owner's sessions only, and only when something actually changed. Known limits: a push job or delivery already queued (or waiting in the 30-second retry) is not re-checked against a mute that began or lapsed since the fan-out ran; archived Conversations are still returned in the list, in their normal place, for the frontend to filter. Tests: `ConversationSettingsTests`.
- Groups (`/api/v1/conversations`, `GroupService`): `POST groups` `{name, userIds}` (name 1-100 characters; 1-255 other verified Users, duplicates and yourself ignored, any unknown or unverified one is a 404 for the whole request) makes the caller ADMIN and the rest MEMBER; `PATCH /{id}` `{name}` renames; `POST /{id}/participants` `{userId}` adds (409 if already in or the group has 256); `DELETE /{id}/participants/{userId}` removes (not yourself: 400, use leave); `POST /{id}/participants/{userId}/promote` makes an ADMIN (idempotent); `POST /{id}/leave`; `GET /{id}` returns one conversation. Admin-only changes give a Participant who is not an admin a 403, a non-participant the uniform 404, and a Direct conversation a 400. Every change takes `ConversationRepository.findByIdForUpdate` and reads the caller's membership again under it. When the last admin leaves, the earliest-joined remaining Participant (ties by user id) becomes admin; when the last Participant leaves the conversation row is deleted and the database cascades to participants and messages. Adding someone back after removal starts a fresh join point. Creating groups is throttled per User (`app.groups.max-created-per-hour`, default 20, failed attempts count, 429 with `Retry-After`). `participants` are listed admins first, then by join time. Responses are built by the package-private `ConversationAssembler` for a given viewer; the join-point rule lives on `Participant` (`canRead`, `readableAfter`). A removed sender's old messages stay, but their name is no longer in `participants` (messages carry only `senderId`).
- Receipts (`POST /api/v1/conversations/{id}/receipts` `{deliveredSeq?, readSeq?}`, `ReceiptService`; see GLOSSARY): each Participant has `last_delivered_seq` and `last_read_seq` (migration `V6`, constraint `joined_after_seq <= read <= delivered`; both start at the join point so pre-join history is never unread). Reports move positions forward only, atomically, with `ParticipantRepository.advanceReceipts` (one `greatest(...)` UPDATE, no conversation lock needed because `last_seq` only grows); a lower or late report is ignored with a 200, reading counts as delivering, a position beyond `last_seq` is a 400, and a non-participant gets the uniform 404. Sending advances the sender's own positions to the new Message, so a reply marks everything before it as read (deliberate, like common chat apps; a product decision to revisit if wanted). A Message's `status` (`SENT`/`DELIVERED`/`READ`, `MessageStatuses`) is set only for its sender and is the minimum of the other Participants' positions (a later joiner can't lower it because their positions start at their join point; with nobody else left it stays `SENT`). It appears on the send response, history pages and the list's `lastMessage`. `Participant` is `@DynamicUpdate` so changing a loaded copy (e.g. a role) can never write stale positions back over the atomic `advanceReceipts` update; keep it that way, and use `Participant.unreadCount(lastSeq)` for the definition. A new Message's status is always `SENT` (nobody can have reported it yet); a retry computes the current status. Positions are reported by clients; nothing marks messages delivered automatically yet (realtime, #11).
- Realtime (#11): the HTTP handshake at `/ws` is public (browsers cannot set headers on it); the access token goes in the STOMP `CONNECT` frame's `Authorization: Bearer` header and `StompAuthInterceptor` checks it (valid, User still exists and is verified). A bad or missing token, a disallowed destination or any frame after the token expired gets an ERROR frame and the socket is closed shortly after (`StompSessions.closeSoon`); `StompSessions.closeExpired()` (every 10s) closes idle sockets whose token expired, and a password reset closes all of that User's sockets on every instance (the `auth.revoked` control event; logout cannot, because sockets are not tied to refresh sessions), so a socket is never a longer revocation gap than REST (up to 15 minutes). A second CONNECT on a session is refused (Spring also answers it with an ERROR). Sockets that never authenticate need no sweep: Spring closes ones that send nothing or only heartbeats. Clients may only subscribe to `/user/queue/events` and `/user/queue/errors` and only send to `/app/conversations/{id}/receipts` (same payload as the REST receipts endpoint) and `/app/conversations/{id}/typing` (the id must be a real UUID; problems come back on the error queue as `{type:"error", status, title, detail, errors?}`). Events are pushed to users, never to conversations: `RealtimeEvents` works out the recipients from the CURRENT participants when the change happens, publishes after the transaction commits (`RealtimePublisher` -> fanout exchange -> `RealtimeListener` on every instance -> `convertAndSendToUser`), so removed or departed Participants stop hearing about a conversation immediately. Event `type`s: `message.created` (`message`, no status), `receipts.updated` (`deliveredUpTo`, `readUpTo`: the `ReceiptFrontier` of everyone else, per recipient; only sent to recipients for whom it actually moved, including when a reply moves the sender's own positions), `unread.updated` (the reporter's own `deliveredSeq`, `readSeq`, `unreadCount`, to the reporter only) and `conversation.changed` (refetch it; also sent to people who just left or were removed). Events are best effort and may arrive out of order: clients order messages by `seq`, treat frontiers as increasing, and refetch and catch up with `afterSeq` after any reconnect (see ADR 0002). The infrastructure components `StompSessions`, `StompAuthInterceptor` and `RealtimeListener` are adapters in `lib`, not services, so they have no interface; services (`RealtimeEvents`) still do. Frames are limited to 16 KB. Not done: automatic delivered marking, rate limits on socket frames.
- Presence and typing (#12): a User is online while any socket of theirs has a live entry in Redis (`presence:sockets:{user}`, a sorted set of socket ids scored by when each lapses, plus `presence:announced:{user}`; all transitions are Lua scripts in `PresenceServiceImpl`, times from the `Clock` bean). `PresenceListener` marks a socket connected/disconnected from Spring's `SessionConnectedEvent`/`SessionDisconnectEvent`; `PresenceHeartbeat` refreshes this instance's live sockets every 10s (one call per User) and an entry lapses after `app.presence.ttl` (30s). **Offline is decided by a sweep, never by an in-memory timer**: the shared sorted set `presence:watch` holds every User who may need to go offline, scored by when they are expected to have no socket (the disconnect time, or the latest lapse time), and every instance runs `PresenceService.sweep()` every `app.presence.sweep-interval` (2s). A User quiet for longer than `app.presence.offline-grace` (5s, tests 1s) is claimed atomically with a lease (`presence:claimed` keeps the original time), their `users.last_seen_at` is stored, `presence.changed {online:false, lastSeenAt}` is announced and the claim is released; if that fails the lease lapses and a later sweep retries (at least once, so clients treat a repeat as no change). So a restart, a crash, a heartbeat landing after a disconnect or a dead instance all end in an announcement. The first socket announces `presence.changed {userId, online:true}` (if publishing fails the flag is cleared so the next heartbeat retries). `last_seen_at` is also written the moment the last socket closes, and only ever moves forward (`UserRepository.updateLastSeen`); `GET` reports offline (with that last seen) from that moment even though the offline announcement waits out the grace period. Instances should run time sync, because entries are scored with each instance's clock. Announcements go to everyone who shares any conversation with the User (`ParticipantRepository.findCoParticipantIds`), online or not, so a user in many large groups produces a long recipient list: revisit if that grows. `GET /api/v1/conversations/{id}/presence` lists the OTHER participants' `{userId, online, lastSeenAt}` (`lastSeenAt` only while offline); participants only, uniform 404 otherwise. - Push (#13): `POST /api/v1/devices` `{token, platform: ANDROID|IOS|WEB}` registers a device (201; 200 and nothing changes if the caller already has the token; 409 beyond `app.push.max-devices-per-user`, 10) and returns `{id, platform, createdAt}`, never the token; `DELETE /api/v1/devices/{id}` is 204 whether or not it existed and only ever removes the caller's own. **A token another User had moves to the caller** (deliberate: the same phone legitimately changes accounts; the token is a secret only that phone's app knows). Tokens go through `@ValidDeviceToken` (4096 max, no NUL; registration takes an advisory lock on the token like Direct conversations do on their key). A password reset deletes every device of the User, and `POST /auth/logout` takes an optional body `{deviceId}` that deletes that device when it belongs to the session being logged out (the refresh cookie proves who that is). Sending a new Message (`MessageServiceImpl`, never a retried one) calls `PushService.messageStored`, which after commit (`AfterCommit.run`, shared with `RealtimeEventsImpl`) only queues a `PushJob` on `messenger.push.messages` (durable, default exchange; a publish failure is logged and never fails the send; there is no outbox, so a broker outage at that instant loses that Message's push). `PushListener` (lib) runs two workers. `PushService.fanOut` takes the CURRENT participants except the sender, drops those with a live socket (`PresenceService.onlineAmong`) and queues one `PushDelivery {deviceId, userId, token, title, body, attempt}` per device on `messenger.push.deliveries`, each device at most once per Message (Redis `SET NX push:queued:{messageId}:{deviceId}`, 1 day, undone if the publish fails); title is the sender's display name (in a Group `Name in Group`), body the first 100 characters plus an ellipsis. If fan-out fails the whole job is retried through `messenger.push.messages.retry`. `PushService.deliver` sends through the `NotificationSender` port, which returns `DELIVERED` or `TOKEN_REJECTED` (the registration that was queued, matched by token AND the queued `userId`, is deleted, so a token that has since moved is untouched) or throws `PushUnavailableException`, the only thing retried (via `messenger.push.retry`). Retry queues dead-letter back to their work queue after `app.push.retry-delay` (30s; tests 500ms) so a retry never blocks a worker; after `app.push.max-attempts` (5), or when even queueing a retry fails, the work is parked on `messenger.push.dead` (nothing consumes it; header `kind` is `job` or `delivery`; it holds the preview text and token, so protect it like the other queues). Any other exception from the provider call is logged and dropped. If even parking fails the exception leaves the listener and the broker requeues the message; only unreadable messages are dropped. `FcmNotificationSender` is only active when `app.push.fcm.credentials-file` (env `FCM_CREDENTIALS_FILE`) is set (FCM `UNREGISTERED`, `INVALID_ARGUMENT` and `SENDER_ID_MISMATCH` mean rejected, everything else temporary; `INVALID_ARGUMENT` can also mean a bad payload, so a payload bug could delete devices); otherwise `LoggingNotificationSender` logs only the title. It has no automated test since it needs real credentials. Tests use `pushes` (`RecordingNotificationSender`: `failNext(n)`, `breakNext(e)`, `reject(token)`, `attempts()`, `all()`) and `pushQueue` (`FaultyPushPublisher`, the real publisher with broker-outage switches). Not done: an outbox for the publish after commit, collapsing several pushes into one per conversation, per-conversation mute or a way to hide the preview, badge counts, pushing other event kinds, purging devices of users who never come back, re-checking at registration that the User still exists, and online status is checked when the worker runs, not when the Message was stored.
- Sessions (`/api/v1/auth`): `POST login` (200 with `accessToken`, `tokenType`, `expiresIn` in the body; 401 for unknown email or wrong password with an identical message, 403 only when the password is right but the email is unverified), `POST refresh`, `POST logout` (204, idempotent; optional body `{deviceId}` to stop push to that device), and `GET /api/v1/users/me`. The frontier (`receipts.updated`: the lowest of everyone else's positions, so in a Group a Message is Read only when every other Participant has read it) lives in the query cache under `["receipts", id]` (`receiptsKey`, set only by events, only ever moving forward, `useFrontier`) instead of being written into the Messages, because an event can arrive before the Message it is about. Known gaps: after a reconnect the frontier is not refetched (the history is only caught up with `afterSeq`), so a mark can stay behind until the next receipt event; a hidden tab is judged by `visibilityState` and `hasFocus()` only. e2e: `watchReports(page)` records the receipts a page sends; a test makes a page "unfocused" by an init script that replaces `document.hasFocus`; a third Participant who needs exact control reports through the backend (`deliveredUpToVia`, `readUpToVia`); on a phone the list is hidden while a Conversation is open, so tests that look at the list go back first (`showIndex`).
- e2e: `waitForForm(page)` (`e2e/support/auth-screens.ts`) waits until React has taken over the form on a freshly loaded page; pressing or typing before that is handled by the browser (the form submits itself, or the typed text is thrown away), which a cold development server makes easy to hit, so tests that go straight to a sign-in or sign-up page call it first.
- Presence and typing (#23, `features/presence`): **Presence** is the generated `presenceOptions({ path: { conversationId } })` query (`usePresence`), fetched for the open Conversation only (the Direct header's `PresenceLine`, a Group's `ParticipantList` inside the header: a `<details>` "Participants (n)" with admins first, "(you)", Admin, and each other person's online dot or last seen). The server only ever lists the Conversation's other Participants, so a person you share no Conversation with is never shown. `presence.changed` events patch every loaded presence query (`allPresenceKey`, via the pure `applyPresence`: a repeat changes nothing, a last-seen time never moves backwards; a query that is being fetched is invalidated instead, like the list) and `catchUp` invalidates them after a reconnect; a `conversation.changed` event refetches that Conversation's presence (someone may have joined). `presenceText` words it ("Online", "Last seen today at 14:02", "Last seen yesterday at …", "Last seen Sun 1 Mar at …", "Offline" for never seen); the offline announcement comes about 7s after the last socket closes (grace period plus sweep), so e2e allows 25s. **Typing** is ephemeral and kept out of the query cache: `createTypingTracker` (framework-free, Vitest) holds who is typing per Conversation and forgets each person 6s after they were last heard (so a lost "stopped" or a dropped connection cannot leave "typing" stuck); `typing.changed` feeds it, a `message.created` from the typist ends their typing at once, and a (re)connection clears it. `TypingLine` (always-rendered `role=status` of fixed height above the composer) shows `typingText` ("Ada is typing", "Ada and Grace are typing", "Ada and 2 others are typing"; the dots are three `motion` spans that pulse, still under reduced motion). **Own typing** goes through `createTypingSender` (framework-free, Vitest): "typing" on the first keystroke, a reminder every 3s from then on (a timer, not tied to keystrokes, so a pause cannot let the others' 6s lapse and flicker the line), "stopped" 4s after the last keystroke, when the box is emptied, on send, and when the view closes (`stop()`, reversible so React's dev remount cannot kill it); it is published over the socket (`connection.publish` to `/app/conversations/{id}/typing`, dropped while disconnected) because the backend has no REST endpoint for it. e2e: `watchTypingSent(page)` reads a page's outgoing typing frames through `routeWebSocket`. Known limits: presence is not refetched for Conversations whose query is not loaded, only the open one is live;  presence announcements carry no timestamp for "online", so a reordered online/offline pair can leave the wrong state until the next announcement or reconnect.
- Groups (#24, `features/groups`): **Creating** is a screen, not an overlay: `/app/new/group` (linked from `/app/new`), `CreateGroupForm`: a name (`checkGroupName`, the backend's rules: not blank, 100 code points, no NUL) and people added by exact email; each address is looked up when added (`POST /users/lookup`) and shown as a named chip (`addPerson` in `members.ts`, pure: yourself, a repeat and the 255-person cap are refused with a reason). The address box is the shared `AddAddressField` (used here and in the panel; not a `<form>`, so Enter adds and never creates or submits anything around it): it checks the address, ignores Add while an add is under way, empties the box only if it still holds the address just added (the person may already be typing the next one) and keeps focus in it (also after a chip is removed). The chip list is kept in a ref as well as in state so an add that finishes later reads the list as it is by then. Create needs a name and at least one person; success refetches the list and opens the Group. **Managing** is `GroupPanel`, the `<details>` "Participants (n)" in a Group's header (it replaces the plain list of #23; `ParticipantList` takes a per-person `actions` render prop): an Admin gets `RenameForm` (a TanStack Form with `groupNameSchema`, keyed by the current name so another Admin's rename replaces what is typed; renaming to the same name sends nothing), Make Admin (accessible name \"Make Admin (Ada Lovelace)\", so it contains the visible text) and Remove per other Participant, which wait for each other (one change at a time), and "Add a person by email" (lookup, then add); every member gets Leave Group, which asks first and says "You are its only Admin, so another member will become Admin" when it applies (the backend decides who: the earliest-joined remaining Participant). What a person may do follows their role in `conversation.participants`; if the server refuses anyway, `groupFailure` (pure, `wording.ts`) puts the reason in place: 403 \"Only an Admin can change this Group.\", 409 already in this Group / the Group is full (256; the only case told apart by the backend's own words), 404 by what was asked (adding or creating: the address, with the same words as starting a Direct conversation; removing or promoting: \"That person is no longer in this Group.\"; otherwise the Group), field errors under the name. A failure clears when the next action starts, when the name or address is edited, or when leaving is cancelled. Nothing is applied to the screen by hand after an action: `useGroupActions` asks for the list (and that Conversation's presence) again, and the backend's `conversation.changed` makes everyone else do the same, so a rename, join, promotion, removal or departure shows live for every Participant; a removed or departed person sees the Conversation leave their list and, if open, \"You are no longer part of this Conversation.\"; leaving navigates to `/app`. The generated mutations (`createMutation`, `renameMutation`, `addParticipantMutation`, `removeParticipantMutation`, `promoteMutation`, `leaveMutation`) are used as they are; adding by email is a custom `mutationFn` (lookup then add). e2e: `e2e/support/navigation.ts` has `index`, `rowFor` and `showIndex` (exact \"Conversations\" link, because a removed Participant's screen also has \"Back to your Conversations\"); a 403 is simulated with `page.route` (the UI never offers a non-Admin a control, so the real server never has to refuse one); a first visit to a page compiles it in development and can take longer than a click assertion allows, so a test that needs a new page `goto`s it. Known limits: only the 256 cap wording is unit-tested (creating a 256-person Group in a browser is not worth it), there is no way to rename or change a Group from a phone-sized header other than opening the panel, and a person who has just been removed sees their panel replaced rather than animated away.
- Polish and accessibility (#25): **Checked automatically** by `e2e/a11y.spec.ts` with axe (`e2e/support/a11y.ts`, WCAG 2.0/2.1 A and AA plus axe's best practices; the Next dev overlay is excluded) on every screen: the public pages with and without their error messages, an empty and a full list, new Conversation, new Group, a Direct conversation, a Group with its panel and the leave question, settings and not found; because the projects cover both themes and both widths this is every screen in the light and dark at phone and desktop width. The same helper fails on the words "chat" or "contact" anywhere in the visible text or in `aria-label`, `title`, `placeholder` and `alt` (the glossary's words are Conversation, Group, Participant, last seen). **Keyboard**: the first Tab stop on every page is a "Skip to content" link to `<main id=main tabIndex=-1>`; the Message history is a focusable `role=region` named "Message history" (a scroll area with nothing to tab to is unreachable for a keyboard user); the global `:focus-visible` outline is the visible focus; the leave question moves focus to Cancel and Cancel gives it back to "Leave Group" (`e2e/keyboard.spec.ts`). **Announcements**: new Messages from other people are written into a visually hidden `role=log` named "New Messages" by `useAnnouncements` (`announce.ts`: `unannounced`, `announcementsFor`, `announcementOf`; not the ones already there when the view opened, not your own; up to three arriving together are read out one line each, at most 200 characters, more than that is just "N new Messages", which is what a catch-up after a lost connection becomes); the typing line is a polite status; every loading line is a `role=status`; the signed-in area says "Checking that you are signed in…" (hidden) instead of rendering nothing. **Reduced motion**: the global CSS rule makes transitions and animations all but instant and the typing dots stand still. `usePrefersReducedMotion` (`lib/use-prefers-reduced-motion.ts`, a `useSyncExternalStore` over `matchMedia`) is used instead of the animation library's `useReducedMotion`, which reads the setting once and never notices a change, and the dots are keyed by the preference because an animation already running is not stopped by removing its `animate` prop. **Show password**: every `Field` of `type="password"` has a button (sign-up and sign-in password, the new password on reset): a button whose name is its visible words (\"Show password\" / \"Hide password\", the \"password\" part visually hidden) toggles the input type; it is a content-named button on purpose, because Playwright's `getByLabel(\"Password\")` also matches `aria-label`s, so an `aria-label` here would collide with every test that finds the field. **States**: `e2e/states.spec.ts` simulates 503 and 429 (with Retry-After) with `page.route` for the list, a Conversation's Messages, the open Conversation and settings: each reads calmly (\"The server is busy. Try again in a moment.\", \"You are doing that too often. Try again in 5 minutes.\") with a Try again that recovers. **Focus after navigation**: `FocusOnNavigate` (in the signed-in shell) moves focus to the new screen's `<h1>` after a client-side navigation (a link, Back), one animation frame after Next's own focus handling; the first screen of a page load is left alone so "Skip to content" stays the first Tab stop; a heading focused by the program shows no ring (`h1[tabindex="-1"]:focus`). e2e also checks 429/503 on sign-in, sign-up ("Too many codes were requested"), starting a Conversation, creating a Group and signing out, and axe on the verified and password-changed views, the new Group form with its errors and the "no longer part" view. Not done: a confirm-password field (the reveal button is the answer to typos), a modal focus trap (there are no modal dialogs: the leave question is inline), and announcing send failures or presence changes.
- Landing page (`/`, `features/landing`): the public front door, replacing the old design sample (which moved to `/design`, unlinked, still used by the theme and layout specs). It follows the app's own tokens (so it is right in light and dark, with glows made from `color-mix` on `--accent`, no new colours) and "Linear-style" in structure: a glowing hero, the product tipped back in 3D, a bento of live mini-demos, three quiet principles, a closing call to action. **One orchestrated moment**: `Hero` sets the headline as the app sets a conversation (a vermilion rail, the viewer's own time in the margin) and it arrives like Messages (`useSequence`: typing dots, a line, typing dots, a line, then the receipt dots go sent, delivered, read); under reduced motion, or without scripts (`<noscript>` forces it visible), the finished headline is just there. `ProductShot` tips `public/landing/conversation-rubric.png` back with `useScroll` and levels it out as it scrolls into place. The image is the app's own screenshot at its real proportions (1559×769, the empty middle of a short conversation is the app's honest empty space) with only the Next dev badge and its faint shadow painted out of the empty sidebar and the wordmark in its header repainted from \"Messenger\" to \"Rubric\" (the word rendered by the app in its own typeface and placed on the old word's baseline; the rest is the owner's own screenshot, names included). The window ends crisp, lifted by a layered shadow (ink for depth, a wash of the accent for warmth): a fade was tried and turned a dark window on light paper into mud, and cutting the blank band out of the screenshot made the window too short and wide, so neither is done. Rename the file when its content changes, because Next's image optimizer caches by URL. On a phone the window is cropped and zoomed in on the Messages. `LiveDemos` draws three demos in the app's own words and marks (`Receipts`, `PresenceAndTyping`, `GroupRoles`), each running only while on screen (`useInView`) and resting on its most complete frame under reduced motion (`useLoop`); they are `aria-hidden` illustrations and the card captions carry the meaning. `SpotlightCard` has a pointer-following light (mouse only). Everything is the `motion` package (`motion/react`, the current Framer Motion), with `MotionConfig reducedMotion=\"user\"` and the reactive `usePrefersReducedMotion`. Session-aware: `AccountLinks` shows \"Open Rubric\" to someone signed in and \"Create an account\" / \"Sign in\" otherwise. Copy only claims what is true (no \"end-to-end encrypted\": the app is not). `e2e/landing.spec.ts` covers the headline sequence, the links (signed out and in), the image, the section headings and anchors, the demos running, the 3D tilt levelling out on scroll, reduced motion and no sideways scroll; axe covers `/` like every other screen.
