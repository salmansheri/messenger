# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A WhatsApp-style messenger app, as a monorepo with one git repo at the root. Domain language lives in `GLOSSARY.md`; the backend plan is GitHub issue #1 with tickets #2-#13 (see Agent skills below). The backend is finished (tickets #2-#13); the frontend is being built from the spec in issue #14 and its tickets #15-#25.

- `backend/` — Spring Boot 4.1.x, Java 25, Maven (package `dev.salman.backend`)
- `frontend/` — Next.js 16 (App Router), React 19, Tailwind 4, TypeScript, Bun

## Backend commands (run from `backend/`)

```bash
./mvnw spring-boot:run                                  # run the app
./mvnw test                                             # all tests
./mvnw test -Dtest=BackendApplicationTests#contextLoads # single test
./mvnw package                                          # build jar
```

- `spring-boot-docker-compose` is on the classpath, so `spring-boot:run` auto-starts `compose.yaml` (Postgres, Redis, RabbitMQ, Mailpit, Grafana LGTM for OpenTelemetry). Redis/RabbitMQ use random host ports and Spring wires them automatically; don't hardcode their URLs in dev. Postgres is pinned to host port `5433` so a database client (DBeaver) keeps working across restarts: `jdbc:postgresql://localhost:5433/mydatabase`, user `myuser`, password `secret`. The root and backend compose stacks would clash on it if both were up at once, like Grafana and Mailpit. Mailpit is fixed at SMTP `1025` (app default) and web UI `http://localhost:8025`. Grafana is on host `3000`.
- Spring only looks for a compose file in the directory the app starts from. `./mvnw spring-boot:run` runs in `backend/` and uses `backend/compose.yaml`; running from the repo root (an IDE's default) uses the root `compose.yaml`, which just `include`s the backend one. The two start under different compose project names (`backend` and `messengerapp`), so their data volumes differ and the fixed host ports (Grafana 3000, Mailpit 1025/8025) clash if both stacks are up at once: stop one (`docker compose stop`) before starting the other.
- A stale Postgres volume from an earlier run can cause `password authentication failed for user "myuser"`; `docker compose down -v` in `backend/` fixes it.
- Tests sit at one seam: the running app's public interface. Extend `support.IntegrationTest` (MockMvc, real Postgres/Redis/RabbitMQ via `TestcontainersConfiguration`). Only email and push are faked: use the `emails` and `pushes` recording senders it exposes (e.g. read a Verification code from `emails.latestTo(...)`). `IntegrationTest.auth()` returns an `AuthClient` that drives the auth endpoints (refresh token passed and read as a cookie) from a unique client IP (so rate limits never leak between tests) and reads codes from the recorded emails. The test context uses a 4-second code TTL (`app.otp.ttl`), so code-expiry tests sleep just over 4s; token expiry is tested by moving the `MutableClock` (`clock.advance(...)`, reset before each test). `IntegrationTest` runs a real server on a random port (`port`) next to MockMvc, so `StompTestClient` can open real WebSockets; Spring's in-memory broker sends no STOMP receipts, so `RealtimeTests.listening` proves a socket is subscribed by publishing probe events through RabbitMQ until one arrives. Run the app against test containers via the `TestBackendApplication` main class.
- Schema is managed by Flyway (`spring-boot-starter-flyway`); put migrations in `src/main/resources/db/migration`. Note that JPA is also present, so don't rely on Hibernate DDL auto-generation.
- `application.yaml` holds JPA validation, virtual threads, problem details, mail host/port, and the `app.*` settings bound by `AppProperties` (JWT and OTP values are placeholders until tickets #3-#4).

## Frontend commands (run from `frontend/`)

```bash
bun dev           # dev server (Turbopack) on port 3001, because 3000 is Grafana's
bun run build
bun run lint      # eslint (generated API code is ignored)
bun run typecheck # tsc --noEmit
bun run test      # Vitest: pure modules only (lib/**, features/**, components/**, *.test.ts)
bun run e2e       # Playwright against the real backend, desktop and phone projects
bun run api       # regenerate lib/api/generated from the running backend's /v3/api-docs
```

- **Next.js 16 has breaking changes from older versions.** `frontend/AGENTS.md` requires reading the relevant guide in `frontend/node_modules/next/dist/docs/` before writing Next.js code. Heed deprecation notices. `next.config.ts` enables `cacheComponents` and partial prefetching: reading `cookies()` or other request data in a layout makes everything under it dynamic, which is why the theme cookie is read by an inline script instead (see below).
- If styles or the theme look wrong after editing CSS in odd ways (or after `bun run build`), delete `frontend/.next`: the dev server's cache can go stale and make e2e tests fail for no code reason.
- The root `.mcp.json` registers `next-devtools-mcp`; use it for Next.js runtime/docs queries when available.
- Port clash: the Grafana LGTM container in the backend compose file maps host port `3000`, the same as `next dev`'s default, so the `dev` script already uses `3001` (the backend allows both origins).
- Frontend tests sit at one seam (see issue #14): the running app in a real browser against the real backend, nothing mocked. **One recorded exception: failure injection at the network edge.** A test may use `page.route` / `page.routeWebSocket` to make a request fail, answer 429 or 503, hold an answer back, lose an answer, or refuse a socket, because the real backend cannot produce those on demand (a 503, a throttle that is deliberately raised in tests, a response that never arrives). The app and the backend stay real, the injected answer is the one the backend itself would give (a problem+json with the real CORS headers and `Retry-After`), and a test never fakes a success or a body the backend would not send. Anything else that needs the backend uses the backend. Vitest is only for pure modules a browser cannot reach cheaply (token single-flight, optimistic-send state machine, event reducer, Zod schemas, theme and problem parsing).

## CI

GitHub Actions (`.github/workflows/ci.yml`, badge in `README.md`) runs on every push to `main` and every pull request; a newer run on the same branch or PR cancels the older one. A `changes` job (`dorny/paths-filter`) reports whether `backend/**`, `frontend/**` or the workflow file changed (a workflow change counts as both) and the jobs run on that: the backend job only when `backend/**` or the workflow changed, so a documentation-only change runs nothing else. Two quick pushes to `main` cancel the first run, so the green run to wait for before closing is the one of the latest push. The backend job is `./mvnw -B -ntp verify` on Temurin 25 with the Maven cache; Testcontainers uses the runner's Docker, as locally (its images, Grafana LGTM included, are `:latest`, so an upstream release can turn CI red with no commit here). On failure the surefire reports are uploaded as the `surefire-reports` artifact (7 days). The image job runs on the same changes as the backend job and builds `backend/Dockerfile` (context `backend/`) with Buildx, never pushing and never logging in to a registry; its layers are kept between runs in GitHub's Actions cache (`type=gha`, `mode=max`), so a code-only change reuses the Maven dependency layer. The frontend job runs only when `frontend/**` or the workflow changed: Bun from `package.json`'s `packageManager` (`oven-sh/setup-bun` with `bun-version-file`), Bun's install cache keyed on `bun.lock`, `bun install --frozen-lockfile` (a lockfile out of step with `package.json` fails it), then `lint`, `typecheck`, `test` (Vitest) and `build`, with no environment beyond `NEXT_TELEMETRY_DISABLED` (the API address stays the default `http://localhost:8080`; the build never calls the backend). The build downloads the fonts through `next/font/google`, so an outage there turns the job red with no commit here. No secrets, no Playwright, no required checks (CI reports, it does not gate), and **failed tests are never retried**: a test that is flaky on the slower runner (the timing-based ones: code TTL, lock timeout, presence sweeps) is fixed. An issue is closed only after its push's run is green. Lint the workflow with `actionlint` after changing it.

## Architecture notes

Backend design (partly implemented; see issue #1 for the full spec):

- REST via `spring-boot-starter-webmvc` plus OpenAPI/Swagger UI (`springdoc-openapi`).
- Realtime: STOMP over WebSocket at `/ws` with Spring's in-memory broker per instance, and a RabbitMQ fanout exchange (`messenger.events`, one private queue per instance) carrying events between instances; see `docs/adr/0002-realtime-events-over-rabbitmq-fanout.md`. Presence lives in Redis (see below).
- Security: stateless Spring Security. Public paths are `/api/v1/auth/**`, health/info, and OpenAPI/Swagger; everything else needs a bearer JWT. Security failures are written as problem+json by `ProblemSecurityHandlers`. JWTs are self-issued (ES256, `JwtConfig`; the signing key comes from `app.jwt.private-key`/`public-key` PEMs, or an ephemeral key is generated with a warning) and validated by the resource-server filter; there is no OAuth2 client. `Clock` is a bean (`JwtConfig`) so tests can move time.
- Errors: all errors are RFC 9457 problem details with `title`, `status`, `detail`, `instance` (no `type` while it is the default). Validation failures add an `errors` map of field to message; unexpected exceptions become a generic 500. All of this lives in `GlobalExceptionHandler`; add domain exception handlers there. Security failures use the same shape via `ProblemSecurityHandlers`. Test-only `ErrorProbeController` (test classpath) exercises these paths.
- Outbound ports `EmailSender` and `NotificationSender` live in `lib`; real implementations are SMTP and (later) FCM.
- PostgreSQL is the primary store (JPA + Flyway); Lombok and MapStruct are wired via a single `annotationProcessorPaths` list in the `maven-compiler-plugin` configuration in `pom.xml` (with `lombok-mapstruct-binding`). Add any new annotation processors there. Packages are by technical layer under `dev.salman.backend` (`controller`, `service`, `repository`, `entity`, `dto`, `exception`, `config`, `lib`). **Every service is an interface in `service` with its implementation named `*Impl` in `service/impl`**; controllers and other services depend on the interface.
- Frontend (#14, `docs/adr/0003-...`): the browser calls the backend directly at `NEXT_PUBLIC_API_URL` (default `http://localhost:8080`, see `.env.example`); the access token lives only in memory and every signed-in screen is a client component. `lib/api` wraps the generated client (general error wording lives in `lib/api/messages.ts`: `messageFor`, `describeWait`; screen-specific wording sits with its feature) (`lib/api/generated`, committed, regenerate with `bun run api` against a running backend): the generator (`openapi-ts.config.ts`) also runs the **TanStack Query plugin**, so every endpoint has generated `…QueryKey()`, `…Options()` (queries), `…InfiniteOptions()` (history, because `beforeSeq` is registered as a pagination keyword) and `…Mutation()` helpers in `lib/api/generated/@tanstack/react-query.gen.ts`, all re-exported from `@/lib/api` next to `sdk`; use those (`useQuery(listOptions())`, `useMutation({ ...signUpMutation(), onSuccess })` then `mutate({ body })`) instead of writing `queryKey`/`queryFn` by hand, and `listQueryKey()` / `meQueryKey()` to find or patch their data (their keys are objects like `[{ _id: "list", baseUrl }]`, so matching a key by hand is wrong). Every call throws on failure (`throwOnError` is the generated default) and one error interceptor in `lib/api/index.ts` turns what is thrown into an `ApiProblem` (`asProblem`: status, title, detail, field `errors`, `retryAfterSeconds` from Retry-After; status 0 means the network failed or the request was cancelled), also declared as TanStack Query's default error type, so `error` is an `ApiProblem` in every query and mutation. Outside hooks call the SDK directly and take `.data` (`(await sdk.report({ … })).data`); there is no `call()` any more. Not API data, so hand-keyed: `["receipts", id]` and `["read-position", id]`. `setAccessTokenProvider` is how the session module supplies the token. Design is "Editorial": paper and ink with one vermilion accent, Fraunces (`font-serif`) for names and headings, Geist for text, Geist Mono for times, no bubbles. Colours are CSS variables in `app/globals.css` (`--paper`, `--ink`, `--ink-muted`, `--rule`, `--accent`, `--on-accent`, `--band`, `--surface`, and `--scrim`/`--on-scrim`, the dark glass and its light ink behind a picture shown full size, the same in every theme: never build that backdrop from `ink`, which is near-white in the dark theme) exposed as Tailwind colours (`bg-paper`, `text-ink-muted`, `border-rule`, `bg-accent text-on-accent`); never hard-code a colour. Two deliberate deviations from the design interview: the accent is a deeper vermilion (`#bf3f1a` light, `#f0704a` dark) than the sketched `#e4572e`, because white text on that fails AA; and the theme is applied by an inline script that reads the cookie in the browser, not rendered by the server, because reading the cookie in the layout would make every page dynamic under Cache Components (the result is the same: no flash, checked at first paint by a test). `frontend/AGENTS.md` keeps only the original Next block: `experimental.agentFeedback` was removed from `next.config.ts` so `next dev` stops writing a block that asks agents to report feedback to the Next.js team; re-enable it only if you want that. Theme is system/light/dark: the `theme` cookie (readable by the page) is applied to `<html data-theme>` by an inline script in the layout head before first paint (`lib/theme.ts`, `THEME_INIT_SCRIPT`), "system" leaves the attribute off so `prefers-color-scheme` decides, and `ThemeSwitch` re-applies it in a layout effect because React's dev remount clears `<html>` attributes. The app is called **Rubric** (a rubric is the red lettering in manuscripts: our vermilion accent on paper and ink); the name is the `APP_NAME` constant (`lib/app-name.ts`), also used by the backend's OpenAPI title and GLOSSARY.md, and the screenshot on the landing page carries it in its header, so a rename means retaking or repainting that image under a new filename. The repository and Java package keep their old names. Use the glossary's words in the UI (Conversation, Group, Participant, last seen), never "chat" or "contact". Forms use TanStack Form (`@tanstack/react-form`; `lib/forms/form-helpers.ts` has `useFormElement` (the form ref and focus-the-first-invalid-field) and `submitHandler`, used by every form) with Zod schemas that mirror the backend's rules (`features/auth/schemas.ts`: email trimmed and lower-cased, display name 1-100 code points, password 8-72 characters and 72 bytes, 6-digit code) as per-field `onDynamic` validators with `revalidateLogic({ mode: "submit", modeAfterSubmission: "change" })` (check on submit, then on every keystroke; **not on blur**: an error line appearing or vanishing as the pointer goes down on the button moves the button away and the press is lost, which looks like a form that does nothing and also leaves the form un-submitted so typing never revalidates); a field's message shows once it is touched (`shownError`), a failed submit focuses the first `aria-invalid` field, and `onSubmit` re-parses the values with the full schema because TanStack Form validates but does not hand you the schema's trimmed/lower-cased output and hands the result to a TanStack Query `useMutation` that owns the request (`isPending` drives the buttons' `busy`, `onSuccess`/`onError` do the navigation and messages; `toProblem` turns any thrown value into an `ApiProblem`). `lib/query/query-provider.tsx` wraps the app in one `QueryClient` with retries off, because a failed call already carries the backend's answer and a person can press the button again. A backend problem's field `errors` go through `useServerProblems` (`features/auth/server-problems.ts`): they show under the matching field until that field is edited, and anything else is one `role=alert` notice above the buttons (the backend's own wording is shown as is, e.g. "must be a well-formed email address", because the client's email check is a little looser than Hibernate's); `features/auth/wording.ts` turns an `ApiProblem` into plain words and a wait into minutes/hours. Pages that read the query string wrap that client component in `Suspense` (Cache Components). Auth screens (#16): `/sign-up` hands the address to `/verify` through this tab's sessionStorage (`features/auth/pending-email.ts`) so it never appears in a URL, history or Referer; the verify screen also works cold (type the address) and ends on a success view that links to `/sign-in` and forgets the stored address. The backend answers every refused code (wrong, expired, too many tries, unknown address, already verified) with the same 400, so the UI cannot tell them apart: it says "wrong or has expired" (`codeMessageFor`) and counts 400s per address itself (`wrong-tries.ts`, limit 5 as the backend allows; resets when the address changes or a new code is sent) to advise asking for a new code, without claiming the code is dead. Buttons take `busy` (`aria-disabled`, not `disabled`) while a request runs, so a double press sends nothing twice and keyboard focus is not lost. e2e helpers: `problem(page)` and `info(page)` select notices inside the main region because Next's route announcer is also a `role=alert`. Next keeps the page you navigated from in the DOM (hidden, so Back restores it), so label and `locator("main")` queries can match two elements after a client-side navigation: use role queries (`getByRole`), which only see what is on screen (`verifyEmailField`). Back after sign-up therefore shows the filled sign-up form, password included, from memory.
- Observability: OpenTelemetry starter exporting to the LGTM container.
